## Verdict
**Overall:** PASS

**The one question — could a silently-wrong-about-a-low defect survive this work as built?**
For the EPIC 8 surface, **no**, and I verified this by running the code myself rather than reading test names:
- **INV-2** (patient readout) refuses at n=149 / Gate-1-closed with **no** `force/override/skip_gate/bypass/gate1_passed` parameter and no env var (`BGMARKOV_FORCE_READOUT`, `SKIP_GATE`, `GATE1_PASSED`, `DEBUG` all set — still raised `GateNotPassed`). Enforced by the single `core.safety.inv2_patient_output_requires_gate1`, not re-implemented in `readout.py`.
- **INV-9** (write-before-return) refuses on **every** path: a `flush` that raises propagates with no return; a `flush` that leaves `prediction_id` unset raises `SafetyViolation`; `serve_prediction` inherits the guarantee because it can only build a `ServedPrediction` from a persisted row. `inv9_prediction_persisted` is called before the physical `return` in `record_prediction` (verified by source-index comparison).
- **Guardrails** refuse rather than guess at the exact boundaries (p=0.39 ⇒ refuse, p=0.40 ⇒ refuse, p=0.41 ⇒ state; conflict gap>1 picks **no** winner, `state=None`; 601 ⇒ INV-6 hard error, 600 ⇒ not; INV-6 checked **first**, so 601+OOD still raises rather than being masked by a refusal).
- **Kill switch** trips on drift and never self-re-arms (5 consecutive good runs left it tripped; only `rearm(operator_confirmed=True)` cleared it).
- **Patient readout** always leads with `Hypoglycaemia risk:` even for a confident hyper prediction (State 5 ⇒ `hypo_risk="reduced"`, headline still hypo-first — commit 182eb05's "reduced" did **not** bury the hypo headline) and carries no `dose/bolus/units/advice` attribute or directive.
- **Shadow dashboard** surfaces `β_insulin < 0` as a boolean alarm and never headlines accuracy.

The residual silent-failure surface is **not** in EPIC 8 code: `require_gate1`/`require_gate2` trust a `Gate1Status.is_open` boolean, and a caller could fabricate `Gate1Status(is_open=True, valid_meals=149, ...)` directly, bypassing the honest `gate1_status()` factory. This is the documented ADR-7 caller responsibility (the invariant checks the boolean; the factory computes it honestly), it is unchanged this epic, and the module-boundary no-bypass tests (no param, no env) all pass. It is equivalent to a caller hardcoding `gate1_passed=True` and is out of the module's contract. Noted, not scored as a finding — but it is the thing the next audit of the API/CLI wiring must confirm the real callers never do.

## Findings (most severe first)

**[SEV: minor] F1 — Every EPIC 8 story doc still marked "Status: In progress" while the epic is Done/Complete.**
Claim vs reality: `docs/traceability.md` and `docs/10-backlog.md` say each S-801..S-805 is "✅ Done" and "EPIC 8 COMPLETE"; but `docs/stories/S-801.md:4`, `S-802.md:3`, `S-803.md:3`, `S-804.md:4`, `S-805.md:4` all still read "**Status:** In progress".
Evidence: `grep -n "Status:" docs/stories/S-80*.md` (all five say "In progress").
Why it matters for her: the story doc is the human-readable "what was built" record; a stale status is exactly the narrative-vs-reality drift that lets a half-finished safety story look tracked. Here the code is in fact complete, so the risk is low — but the habit is the dangerous one.
Suggested owner: **BA**.

**[SEV: minor] F2 — DL-029 going-forward rule only partially applied: BA-owned story docs still land in SDET `test()` commits.**
Claim vs reality: DL-029 (set in `ca44ef0`, in force before EPIC 8 began) says `docs/**` changes land in a `docs(...)` BA commit distinct from `test(...)`. But every EPIC 8 RED commit created a new BA-owned story doc inside an SDET `test(...)` commit: `7841427` (S-801.md, "new file"), `d12a1da` (S-802.md), `d892532` (S-803.md), `118a5c8` (S-804.md), `b60c635` (S-805.md).
Evidence: `git show --name-only <sha>` for each; `git show 7841427 -- docs/stories/S-801.md` shows `new file mode 100644`. Note the decision-log/traceability half of DL-029 **is** followed (separate `docs()` BA commits exist).
Why it matters for her: attribution is a safety signal — the audits reconstruct who-did-what from commit labels, and a BA artifact under a `test(...)` label erodes that signal, precisely what DL-029 exists to prevent.
This is a **judgement call**, not a clear defect: the story-restatement is arguably part of establishing RED. Options: (a) clarify DL-029 to explicitly exempt the story-doc restatement that accompanies the RED commit; or (b) split the story doc into its own `docs(...)` BA commit ahead of the RED test, per CLAUDE.md's TDD-loop step 1.
Suggested owner: **BA** (record the decision and route).

## What I could NOT verify
- **Real-caller gate honesty at the API/CLI boundary.** EPIC 8 is library code; I verified the `readout.py`/`bolus.py`/`predictions.py` functions in isolation. I did **not** verify that the (future/other-epic) API and CLI callers always build `Gate1Status`/`Gate2Status` from the honest `gate1_status()`/`gate2_status()` factories reading live DB data, rather than fabricating `is_open=True`. That is where the trusted-boolean residual (see Verdict) would actually bite; it is not in EPIC 8's scope.
- **Transactional durability of the INV-9 write.** `record_prediction` uses `session.flush()` (writes + assigns PK within the transaction) before returning; I did not test the case where an outer transaction later rolls back after the prediction was returned. INV-9 as specified is "written to `prediction_log` before returned", which `flush` satisfies; commit/rollback semantics are a broader concern outside this story.
- **a11y/e2e rendering** of the readout (colour-only signalling in the actual browser) — Playwright suites deselected. The dataclass carries text labels (`hypo_risk`, `severity`) and the unit test asserts they are non-empty strings, but the rendered surface was not exercised here.
