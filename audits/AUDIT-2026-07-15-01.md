## Verdict
**Overall:** PASS-WITH-CONCERNS

**The one question — could a silently-wrong-about-a-low defect survive this work as built?**
**No — not in what is built so far.** The two highest-risk silent-low vectors for this stage are
both genuinely defended, not merely claimed:
1. **ADR-8 timestamp corruption** (conflating log time with event time, which would silently
   fabricate `bolus_offset_min`/`elapsed_min`): the write path (`data/recording.py`,
   `core/timestamps.py`) uses reported times only; `datetime.now()` appears in exactly one
   sanctioned place (`core/clock.py`, for `logged_at`); an AST guard scans `data/` and every
   source package and fires on `now()` bound to any clinical timestamp. I ran the guard suite
   (passes) and grepped the tree myself (only `clock.py`).
2. **INV-7 silent deletion of lows**: `inv7_rescued_excluded_and_retained` is a single function
   in `core/safety.py`, and it is *actually wired* into `data/repositories.py::get_training_set`
   (not re-implemented inline). `get_hypo_events()` and `get_training_set()` both exist. The
   100-meals/20-rescued regression guard and an adversarial monkeypatch "wiring-bites" test both
   exist and pass.

The residual concerns are process/hygiene (TDD red-first and ownership discipline breached on a
few commits, and BA did not record them), plus latent-but-acknowledged vacuous guards for
not-yet-written code. None of these is a hole a silent low currently slips through, but they are
exactly the kind of discipline erosion that, uncorrected, makes a future silent failure quiet
instead of loud — hence PASS-WITH-CONCERNS rather than a clean PASS.

## Findings (most severe first)

**[SEV: major] F1 — RED-first and "Dev never edits tests/" breached on several GREEN commits; not recorded by BA.**
Three implementation (GREEN) commits modified files under `tests/`:
- `9eff0ec` feat(S-201) GREEN (Dev) — edited `tests/a11y/conftest.py`,
  `tests/integration/test_schema.py`, `tests/safety/test_config_frozen.py`,
  `tests/safety/test_safety_invariants.py`. **Content: pure isort import-reordering** (data/
  became first-party). Harmless, but it is Dev touching `tests/`, including a safety test file.
- `b4e4cbf` feat(S-103) GREEN ("Dev+SDET") — **added new hazard-branch tests**
  (`test_icr_non_positive_raises`, `test_non_positive_curve_constants_raise`) in the *same
  commit as the validators they exercise*. Those specific cases were therefore never committed
  RED-first; the "seen to fail against a guard-stripped module" claim is prose in the commit
  message, not a red commit in history.
- `790e385` feat(S-202) GREEN (Dev) — **created `tests/unit/test_clock.py`** (a new test file)
  inside the implementation commit.
Claim vs reality: `CLAUDE.md` says "Dev never edits `tests/`" and "green-before-red is a process
failure … the test is deleted and rewritten"; the traceability/story prose says every story was
"RED-first throughout." Evidence: `git show --name-only` on the three SHAs above. Why it matters
for *her*: RED-first and the SDET/Dev separation are the mechanism that stops a test from being
shaped by (and therefore blind to) the code it is supposed to challenge — the discipline that
keeps a wrong-about-a-low bug loud. The *content* here is benign (isort, positive-value guards,
an existence test), so this is not itself a silent-low hole; it is a discipline erosion that BA,
whose job is to flag exactly this, did not record in the decision log. Suggested owner: **BA**
(record the deviation; decide whether the S-103 hazard-branch cases and `test_clock.py` need
re-authoring RED-first), with **SDET/Dev** to observe the boundary going forward.

**[SEV: minor] F2 — Part of the S-302 "RED" suite was already green when authored.**
`tests/integration/test_bolus_timing.py` asserts the server rejects an absent/null
`bolus_offset_min` with 422. That behaviour was already delivered by S-301's `MealCreate` schema
(`bolus_offset_min: int`, no default) at commit `f59c32c`, *before* the S-302 RED commit
`fabd7f5`. So those server-side cases could not have been red at authoring; only the client-side
e2e blocking (added in GREEN `f10cccc`) was genuinely new. Evidence: `MealCreate` in
`api/schemas.py:30`; S-302 GREEN diff touches only `api/static/*` + `index.html`. Why it matters:
defense-in-depth is fine, but a "RED" label on already-green assertions weakens the signal that
red-first is being honoured. Suggested owner: **BA/SDET** (accuracy of the RED claim).

**[SEV: minor] F3 — Two forbidden-pattern guards are vacuous until EPIC 4/5 names them.**
`detect_pre_bg_to_binner` scans only for function names in `_BINNER_NAMES`, and `detect_manual_iob`
protects IOB-assignment code that does not exist yet. Both pass today because the code they guard
is unwritten. This is acknowledged in `docs/traceability.md` (watch-list) and the test comments,
but there is no *failing* reminder — if S-404/S-501 name the binner something not in the set, the
guard silently keeps passing. Evidence: `tests/forbidden/test_forbidden_patterns.py:33-36,194-205`.
Why it matters for *her*: binning `pre_bg` on the input path discards exactly the low-BG resolution
the model needs; the guard meant to catch it must be armed before that code lands. Suggested owner:
**SDET** (add the binner name to `_BINNER_NAMES` in the same PR that introduces it; consider a
guard that fails if no binner is found once EPIC 4 begins).

**[SEV: minor] F4 — INV-7's "dropped-from-hypo" branch is structurally unreachable via the wired path.**
In `data/repositories.py`, both `rescued_meal_ids` (from `get_rescued_meals`, i.e.
`hypo_treatment == True`) and `hypo_event_ids` (from `get_hypo_events`, which includes every
`hypo_treatment` meal) derive from the same `hypo_treatment` flag. So a rescued meal is always in
`hypo_events` by construction, and the `rescued − hypo` branch of `inv7_rescued_excluded_and_retained`
cannot fire through this call site. The regression guard catches the *leak-into-training* vector
(counts 80/20 correctly) and the unit test covers the drop branch directly, so INV-7 itself is
sound — but the *feature-level* protection against "a future refactor deletes rescued rows from the
DB" is thinner than it looks, because that vector removes the rows from both lists at once.
Evidence: `data/repositories.py:53-64,78-82`; `core/safety.py:112-138`. Why it matters: the
catastrophic case the invariant names ("silently deletes every low she ever had") is a DB-level
deletion, which this wiring would not detect. Suggested owner: **SDET/Dev** (consider a guard that
reconciles rescued-meal *rows* against an independent source, e.g. hypo-rescue capture in S-305).

**[SEV: minor] F5 — Tap-count assertion is a hand-maintained counter, not instrumented.**
`test_repeat_meal_in_at_most_four_taps` increments a local `taps` variable by hand
(`taps += 2  # (the preset click, then the submit below)`) rather than counting actual DOM
interactions. The clicks are real and the flow works (test passes against Chromium), but the
budget assertion is only as honest as the manual bookkeeping. Evidence:
`tests/e2e/test_meal_log_flow.py:15-28`. Why it matters: adherence is the binding constraint for
ever reaching Gate 1; a drifting tap count would not be caught. Suggested owner: **SDET**
(instrument the count, or assert on the number of required interactive controls).
