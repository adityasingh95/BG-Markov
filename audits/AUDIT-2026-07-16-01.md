## Findings (most severe first)

**[SEV: major] F1 — S-306 introduced a new clinical timestamp (`bg_after_time`) but did NOT arm the most-important forbidden-pattern guard for it.**
Claim vs reality: `docs/09-test-plan.md` §6 and `CLAUDE.md` make `datetime.now()` on a
clinical timestamp "the single most important" guarded pattern, and the charter
requires that each forbidden pattern "have a test that fires on violation." The
guard's target set is `_CLINICAL_TS = {"datetime", "pre_bg_time", "post_bg_time",
"bolus_time", "bolus_datetime", "time_taken"}` (`tests/forbidden/test_forbidden_patterns.py:27-29`).
S-306 added `correction_event.bg_after_time` — a **REPORTED** value (`data/tables.py:188`,
comment "# REPORTED") — but did not add it to the set. Evidence (demonstrated, this
session):
```
detect_datetime_now_on_clinical_ts(ast.parse("CorrectionEvent(bg_after_time=datetime.now())")) -> []   # MISS
detect_datetime_now_on_clinical_ts(ast.parse("event.bg_after_time = datetime.now()"))          -> []   # MISS
detect_datetime_now_on_clinical_ts(ast.parse("MealEvent(post_bg_time=datetime.now())"))        -> ['post_bg_time=now()']  # caught
```
The shipped code is correct — `record_correction_followup` (`data/recording.py:106-114`)
stores the reported `bg_after_time`; no `now()` touches it. So this is **not a live
silent-low defect**. But `bg_after_time` is the timestamp of the +4 h reading used to
close out a correction event that feeds the ISF signal ("the most dangerous number");
the most natural wrong refactor — "just stamp it when she enters it" —
(`bg_after_time = datetime.now()`) would sail past the guard with no error and no
warning. Why it matters for *her*: the guard exists to make exactly this kind of
timestamp fabrication *loud*; leaving the newest reported timestamp outside it
re-opens, for one field, the silent-corruption channel ADR-8 closes everywhere else.
Suggested owner: **SDET** (add `bg_after_time` to `_CLINICAL_TS`; consider a
meta-test that every ORM column commented "# REPORTED" appears in `_CLINICAL_TS`, so
the next reported timestamp can't be added without arming the guard).
