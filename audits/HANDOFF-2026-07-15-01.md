### H4 — Close the row-level deletion vector for INV-7
- **Do:** In `data/repositories.py`, both `rescued_meal_ids` and `hypo_event_ids`
  derive from the same `hypo_treatment` flag, so a rescued meal is always in
  `hypo_events` by construction and the "rescued − hypo" drop-branch of
  `inv7_rescued_excluded_and_retained` cannot fire via this call site. INV-7 itself
  is sound (unit test + 100/20 regression guard both pass) — but the *catastrophic*
  case it names ("silently deletes every low she ever had") is a **DB-level row
  deletion**, which this wiring would not detect. Add a check that reconciles
  rescued-meal *rows* against an independent source (e.g. the hypo-rescue capture
  arriving in S-305), rather than against a list derived from the same flag.
- **Where:** `data/repositories.py:53-64,78-82`; `core/safety.py:112-138`. Natural
  home is S-305 (Hypo rescue capture).
- **Why (for her):** the exact failure INV-7 exists to prevent is a low disappearing
  from the data entirely; the current wiring can't see that vector because it removes
  the row from both lists at once.
- **Done when:** a test deletes/omits rescued rows at the DB level and asserts the
  reconciliation catches the count mismatch **without** relying on both lists sharing
  the `hypo_treatment` derivation. (This is a judgement call on placement — do it as
  part of S-305 if that's cleaner than a standalone guard; either is acceptable.)
