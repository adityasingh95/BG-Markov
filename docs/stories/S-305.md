# S-305 [SAFETY] — Hypo rescue capture

**Epic:** 3 (Logging & Durability) · **Safety story:** Yes · **Status:** In progress
**Requirements:** REQ-012 · **Invariant:** INV-7 · **Closes:** DL-019 (audit 2026-07-15-01 H4)

> A hypo rescue is the single most important event this system records: it *is* a
> low. The obvious refactor — "invalid rows get dropped from training" — silently
> deletes exactly the lows the system exists to predict. INV-7 exists to make that
> loss **loud**. This story makes INV-7 able to hear the one loss it currently
> cannot: a rescued **meal row that disappears from the database entirely**.

## Story
Capture a hypo rescue during the post-meal window (flag + grams) and — the
[SAFETY] core — record each rescue in an **independent, append-only ledger**
(`hypo_rescue_log`) so INV-7 reconciles the rescued set against a source that does
**not** vanish when the meal row does.

## Requirement source
- **REQ-012** — a hypo rescue during the window is captured (flag + grams).
- **INV-7** — hypo-rescued meals are excluded from outcome regression but
  **retained as hypo events**.

## Background — why more than a flag (audit H4 / DL-019)
The capture UI (post-meal form) and storage (`meal_event.hypo_treatment` +
`hypo_treatment_g`) already landed in **S-303**. But the INV-7 *wiring* had a hole
the audit found (H4):

> In `data/repositories.py`, `get_rescued_meals` and `get_hypo_events` both derive
> "rescued" from the **same** `hypo_treatment` flag. So a rescued meal is in the
> hypo set *by construction*, and the `rescued − hypo` drop-branch of
> `inv7_rescued_excluded_and_retained` cannot fire via this call site. The
> **catastrophic** case INV-7 names — a low disappearing from the data entirely —
> is a **DB-level row deletion**, which this wiring cannot detect: it removes the
> row from *both* lists at once, so the counts still agree.

The fix (per the auditor's decision, DL-019): an **independent record** of rescued
events to reconcile rescued *rows* against, so a count mismatch is caught without
both lists sharing the `hypo_treatment` derivation.

## Design
1. **`hypo_rescue_log`** — a new append-only table, *deliberately independent* of
   `meal_event`. `meal_id` is stored as a **plain integer reference, not a
   cascading FK**, so deleting a meal row cannot erase its rescue record. Columns:
   `rescue_id` (PK), `meal_id`, `grams`, `logged_at` (system clock — an audit
   write time, ADR-8-correct; there is no fabricated clinical timestamp).
2. **Write path.** When the post-meal endpoint captures a rescue
   (`hypo_treatment = true`), it appends a `hypo_rescue_log` row (grams carried
   through). `record_hypo_rescue` follows the S-202 clock-injection discipline.
3. **INV-7's rescued set now comes from the union** of *currently-flagged* meal
   rows **and** the independent ledger:
   `get_recorded_rescue_meal_ids = {flagged meal_ids} ∪ {ledger meal_ids}`.
   `get_training_set` feeds that union into the existing
   `safety.inv7_rescued_excluded_and_retained`. **No invariant is
   re-implemented** — only the *source* of one of its inputs is made truer.

## Written invariant argument (why INV-7 now holds) [SAFETY]
INV-7's function is unchanged; it still lives once in `core/safety.py` and still
raises on `rescued & training` (leak) or `rescued − hypo` (drop). What changes is
that `rescued_meal_ids` is now sourced from a place that survives the two ways a
low can silently disappear:

- **Row deletion (the H4 gap).** A rescued meal row is hard-deleted. The
  flag-derived `hypo_event_ids` loses it (row gone); the ledger still lists it, so
  `rescued − hypo` is non-empty ⇒ **`SafetyViolation`**. Previously both lists
  lost it together and the check was vacuous.
- **Flag cleared (tamper / mis-edit).** `hypo_treatment` is set back to false so
  the meal would re-enter training. The ledger still lists it ⇒ `rescued & training`
  is non-empty ⇒ **`SafetyViolation`**. A recorded low must be *explained*, not
  silently removed; surfacing it loudly is the correct, conservative default for a
  patient who cannot feel a low. (An operator reconciliation path for a genuine
  mis-tap is future scope, not this story — the invariant's job here is detection.)
- **Happy path stays green.** A captured rescue is flagged, ledgered, excluded
  from training (the `rescued` exclusion reason), and present in hypo events — all
  three lists agree ⇒ no raise. The S-203 `100 meals / 20 rescued` regression
  guard still passes unchanged (flag-driven exclusion is untouched; the ledger
  union only *adds* protection).
- **No bypass.** The ledger is append-only; the reconciliation is set-based on
  `meal_id`, so duplicate appends are harmless and there is no flag, config, or
  fixture that removes a `meal_id` from the rescued set once recorded.

## TDD strategy (SDET, written first — seen to fail)
`tests/integration/test_hypo_rescue.py`:
- **Schema/migration:** `hypo_rescue_log` is in `Base.metadata` **and** created by
  the Alembic migration `head` on an empty DB. (RED: table + migration absent.)
- **Independence:** `hypo_rescue_log.meal_id` is a plain column with **no
  cascading FK** — a deleted meal row leaves the rescue row intact.
- **Write path:** `record_hypo_rescue` writes an independent row (meal_id, grams,
  `logged_at` from an injected clock).
- **API:** PATCH post-bg with `hypo_treatment = true` appends exactly one
  `hypo_rescue_log` row carrying the grams.
- **★ H4 row-deletion guard (load-bearing — do not delete):** a rescued meal +
  its ledger row; hard-delete the meal row; `get_training_set` ⇒ `SafetyViolation`
  (`rescued − hypo`). This is the case the old wiring could not catch.
- **Flag-cleared guard:** ledger retains the rescue; `hypo_treatment` cleared and
  the meal otherwise valid; `get_training_set` ⇒ `SafetyViolation` (leak).
- **Union accessor:** `get_recorded_rescue_meal_ids` = flagged ∪ ledgered.
- **Regression untouched:** the S-203 100/20 guard and the existing INV-7 leak
  test still pass.

**RED evidence:** `hypo_rescue_log`, `record_hypo_rescue`, and
`get_recorded_rescue_meal_ids` do not exist ⇒ import/attribute errors ⇒ tests fail
before implementation.

**Adversarial angle:** the tempting shortcut is "the flag already excludes rescued
meals — INV-7 is fine." It is fine only while every rescued row is physically
present. The whole point of an *independent* ledger is the day a row is not.
