# S-1023 — The browser run records itself

**Epic:** 11 · **Safety story:** No · **Status:** ✅ Done (2026-07-31) ·
**Requirements:** REQ-057, `09 §2.1` · **Records:** DL-061

> Every browser assertion this project makes is currently reported as a sentence. When
> `test_post_bg_form_asks_reported_time_and_saves` was green on the toast *"Could not
> save"*, **the run looked exactly like a passing run.** There was nothing to go back and
> watch.

## Story
A browser run leaves a **video and a trace** behind, so a failure can be watched rather
than reconstructed, and the demo can be shown rather than described.

---

## Why this is worth a story rather than a flag

Two different needs, one mechanism:

- **Testing.** A flaky or surprising browser failure is the hardest kind to diagnose from a
  stack trace, because the interesting state — what was on screen, what the network did, what
  the DOM looked like one action earlier — is gone by the time the assertion fires. A
  Playwright **trace** keeps all three, per action.
- **The demo.** Screenshots have carried every demo so far. They cannot show *sequence*:
  that the toast appeared **after** the click, that the button greyed out **during** the
  request, that the second tap did nothing. A **video** shows exactly that, and the S-1019
  double-tap is a thing you have to watch to believe.

★ **And a specific trap this project has already fallen into twice.** Recording that is
declared and never produced is the same "declared and unconnected" failure as
`idempotency_key` (S-1016) and the never-called `serve_meal_prediction` (S-1015): the flag
exists, the docs say runs are recorded, and the directory is empty. So the acceptance
criterion is not *"recording is configured"* — it is **"a file exists on disk afterwards"**.

## Acceptance criteria

1. Recording is **opt-in**, by environment variable. CI stays fast by default; video and
   trace cost real wall-clock and disk.
2. When it is **off**, no video is recorded and no trace is written — asserted, so the
   default cannot silently become the slow one.
3. When it is **on**, a browser test leaves a **`.webm`** and a **`.zip` trace** named after
   the test.
4. `scripts/demo_ui.py --record DIR` produces a watchable walkthrough: a step banner burned
   into the page so the video is self-describing, and a slower cadence so a human can follow.
5. The banner cannot affect what is measured — no layout shift, no horizontal overflow, and
   it is removed before any geometry assertion.
6. Artifacts are **git-ignored**. A 12 MB video in the history is a bad trade.

## Design

`tests/conftest.py` gains `new_recorded_context()` / `close_recorded_context()`, used by both
the a11y and e2e `page` fixtures — one implementation, so a suite cannot be *"the one that
isn't recorded"*. The video handle is captured **before** `context.close()`, because the
context empties its page list on close and the file is only finalised afterwards.

## TDD strategy (SDET first — written and seen to fail)

`tests/e2e/test_recording.py`
- **★ With recording on, a `.webm` and a trace `.zip` exist on disk after the context
  closes.** The assertion is on the FILE, not on the option being set — "configured" and
  "produced" have already diverged twice in this codebase.
- **★ With recording off, `page.video` is `None` and no trace file is written.** The
  reverse guard: an always-on recorder would quietly triple CI time and nobody would look at
  the artifacts anyway.
- The trace is non-trivial (a zip with entries), not a zero-byte placeholder.

**Adversarial angle.** (a) **Setting `record_video_dir` and never calling `save_as`** — the
video lands under a random hash filename or not at all, and the test that only checks the
option passes. (b) Closing the context before reading `page.video`, which loses the handle.
(c) A banner injected with `position: absolute`, which grows the page and breaks the 200 %
overflow assertions.

## Outcome (BA, 2026-07-31)

**Done.** `tests/conftest.py::new_recorded_context` / `close_recorded_context`, used by the
a11y and e2e `page` fixtures and by `scripts/demo_ui.py`. Records **DL-061**.

```
BGAPP_BROWSER_ARTIFACTS=./browser-artifacts pytest tests/e2e
python -m scripts.demo_ui --record ./demo-ui-recording --slow-mo 220
playwright show-trace ./browser-artifacts/trace/<test>.zip
```

Measured on a real run: 8 e2e tests → 8 named videos, 8 named traces, **11 MB**. The demo
walkthrough → a 3.2 MB video and a 15 MB trace, plus a 254 KB video for the Kolkata phone.

### ★ Found by running it, in the first thirty seconds
`save_as` **copies**. The directory came back with **four** videos for two contexts —
`demo-walkthrough.webm` beside `2b487ebe518b47….webm`, identical bytes. A directory holding
both is precisely the confusion the naming existed to prevent. SDET added
`assert videos == ["on.webm"]`, which went red immediately; Dev added `video.delete()`.

Worth noting *why* the original three tests missed it: they asserted **the named file
exists**, which is true whether or not the unnamed one also does. The assertion that
catches it is about what is **absent**, and absence is the thing tests forget to check.

### The narration decision
The demo burns a caption into the page. `position: fixed; left: 0; right: 0` — exactly
viewport-wide, so it cannot create horizontal overflow — and it is **removed before every
geometry assertion**, so the 390px and 200%-zoom checks measure the layout and not the
narration. It is drawn only while recording; an ordinary run is unchanged.

### Still open
- CI does not record. It could on failure only (`--record-on-failure` semantics), which is
  where a trace is worth the most; not done, because CI has never yet failed on a browser
  test and building for a case nobody has hit is how unused machinery accumulates.
