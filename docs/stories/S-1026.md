# S-1026 — A non-technical tester can run it, and can reset it

**Epic:** 11 · **Safety story:** **Yes — destructive action without a terminal** ·
**Status:** In progress (2026-08-06) · **Requirements:** REQ-056, `06 §7` · **Records:** DL-064

> `bootstrap.sh` is one command, and a command is still a terminal. The person who will do
> the functional testing does not open Git Bash, does not know what a branch is, and will not
> know that Ctrl-C stops a server.

## Story
A non-technical tester on Windows double-clicks one icon, the app opens in their browser, and
they can **clear the data and put it back** without typing anything.

**Decided with the operator (2026-08-06):** the tester is a lay person, not the patient — so
the operator screens are in scope and the word "model" may appear. Windows only. Demo data by
default, with reset and restore available.

---

## Written safety argument

### Putting a destructive action one double-click away

Everything else in this story is convenience. **Reset is not.** `dev.sh reset` is safe partly
because reaching it requires a terminal, a path, and typing `DELETE` — three filters that a
person who should not be deleting anything will fail. A `Reset.cmd` sitting in a folder next
to `Start.cmd` has none of them, and the two icons are adjacent and similarly named.

The database it could destroy is not equivalent to the one it is meant to destroy:

| File | What it is | Deleting it costs |
|---|---|---|
| `bgapp-demo.db` | 240 days of synthetic data | seconds — it is regenerated from a seed |
| `bgapp-dev.db` | **the real-capture path** | **her records. There is no seed.** |

So the guard is not the confirmation prompt. **The guard is that reset refuses outright to
touch a database that is not marked as demo data.** A tester who clicks the wrong icon gets a
refusal, not a prompt they can dismiss — because the prompt is exactly what a person clicking
through a task will click through.

This reuses `is_demo_database()` (S-1024) rather than re-deriving "is this safe to delete".
The mark lives in the database, so it travels with the file: rename it, move it, open it a
month later, and it still says what it is.

### Why the launcher must import nothing

`run.py` runs **before anything is installed** — that is its whole job. A single
`import fastapi` at the top makes it crash on exactly the machine it exists to set up, and the
crash is a traceback, which is the thing this story is trying to eliminate. Stdlib-only is
therefore a structural property with a test, not a convention.

It reaches project code by **subprocessing into the venv's Python**, which is also why the
demo-marker check does not drift: `run.py` never re-implements it, it calls it.

### Why not a prompt-free experience

The launcher installs Python. That keeps `bootstrap.sh`'s rule — the exact command is shown,
and it runs only after a typed `YES`. A double-click that silently installs software is worse
than a terminal, not better, because nothing was read.

## Acceptance criteria

1. `Start BG-Markov.cmd` — double-click: checks, installs if needed, seeds, serves, **opens
   the browser by itself**.
2. It says, in plain words, to leave the window open and close it to stop.
3. `Restore demo data.cmd` — rebuilds `bgapp-demo.db` from the seed.
4. `Reset to empty.cmd` — deletes the demo database after a confirmation.
5. **★ Reset refuses a database that is not demo-marked.** No prompt, no override.
6. `run.py` imports **only the standard library** at module level.
7. No known failure produces a traceback. Each is a sentence and an instruction.
8. `.cmd` files are CRLF-encoded.
9. `docs/USER-TEST.md` — a functional test script for a lay tester.

## TDD strategy (SDET first — written and seen to fail)

`tests/integration/test_user_launcher.py`

- **★ `run.py` is stdlib-only**, proven by parsing its AST for module-level imports and
  checking each against `sys.stdlib_module_names`. A grep for `import fastapi` would pass a
  file that imported `pandas`.
- **★ Reset refuses an unmarked database.** Build one that is *not* demo-marked, run reset,
  assert the file **still exists** and the exit is non-zero. Assert on the file, not the
  message — a script that prints a refusal and deletes anyway says the same words.
- **★ Reset deletes a marked one**, so the guard is a guard and not a broken feature. A test
  for the refusal alone is satisfied by a reset that never works.
- `.cmd` files end lines with CRLF. A batch file with Unix line endings fails on the first
  label or `goto` with a message that reads as a corrupt download.
- The `.cmd` files do not assume `python` is 3.12 — the tester's machine is the operator's
  machine, which had 3.11.

**Adversarial angle.** (a) The refusal downgraded to a prompt "so the tester can get on with
it" — the test asserts the file survives, which no prompt satisfies. (b) An import added to
`run.py` later, once the venv "is always there anyway". (c) Reset that unlinks the file before
checking the mark. (d) A `.cmd` rewritten by an editor that normalises line endings.
