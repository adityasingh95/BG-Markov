# S-304 [SAFETY] — ★ Backup + restore drill

**Epic:** 3 (Logging & Durability) · **Safety story:** Yes · **Status:** In progress

> **Data loss is the top failure mode.** ~3 months of her life is at stake. A
> laptop is *more* fragile than a VPS — dropped, stolen, spilled on. Backup is
> not hardening; it is whether the project exists (`06 §5`). **An untested backup
> is not a backup.**

## Story
Give her data three layers of durability and — critically — **prove the restore
works before there is anything to lose**. The single-file SQLite design exists so
this is solvable: one file, one consistent snapshot.

## Requirement sources
- **REQ-050** — hourly consistent DB snapshot to a cloud-synced folder; `app.db`
  **never** inside that folder.
- **REQ-051** — **a restore drill is executed in month one**, before real data
  exists.
- **REQ-052** — nightly CSV export; her data must outlive the code.

## Acceptance criteria (backlog)
- [ ] `app.db` **never** in a synced folder (guarded).
- [ ] Hourly `sqlite3 .backup` → synced folder (`cli backup`).
- [ ] Nightly CSV export (`cli export`).
- [ ] `cli restore-drill`.
- [ ] **★ THE STORY IS NOT DONE UNTIL THE DRILL HAS BEEN RUN FOR REAL** — month
      one, before there is data to lose. **BA logs the date.**

## Written durability argument (why this is safe) [SAFETY]
1. **Live DB out of the sync path.** `06 §5`: syncing a file mid-write corrupts
   SQLite. So `app.db` must never live in a cloud-synced folder — only the
   consistent `.backup` snapshot goes there. `cli.backup` **refuses** (raises
   `SyncedFolderError`) if the live DB path looks synced (Dropbox / Google Drive /
   OneDrive / iCloud / …). A test proves the refusal.
2. **Consistent snapshot even during a write.** The hourly backup uses SQLite's
   **online backup API** (`sqlite3.Connection.backup`), which copies a
   transaction-consistent image while a writer is active. A test writes
   concurrently and asserts the snapshot passes `PRAGMA integrity_check` and
   contains the rows.
3. **Restore is faithful.** The drill restores the snapshot and checks
   `integrity_check == ok`, the restored file is **byte-identical** to the
   snapshot, and the restored **data dump is identical** to the source. A test
   asserts all three.
4. **Format-rot insurance.** The nightly CSV export writes one file per table
   (header + rows) so her data outlives the code and the operator's memory of it.

## TDD strategy (SDET, written first — seen to fail)
`tests/safety/test_backup_restore.py`:
- `app.db` under a `Dropbox/` path ⇒ `cli.backup` raises `SyncedFolderError`; a
  normal path is accepted.
- Backup taken **while a writer is inserting** ⇒ snapshot `integrity_check == ok`
  and holds the committed rows.
- `run_restore_drill` ⇒ `ok == True`: integrity ok, snapshot bytes == restored
  bytes, and source dump == restored dump; per-table row counts reported.
- `export_csv` ⇒ a `<table>.csv` per table with a header row.

**RED evidence:** the `cli` package is absent ⇒ import error ⇒ tests fail.

## ★ The drill is executed for real
Per REQ-051 / the backlog's hard rule, S-304 is **not done** until the restore
drill has actually run. It is executed in this session against a real sample DB;
the command, output, and **date** are recorded in
`docs/durability-drills.md` and the decision log. Re-run monthly thereafter.

**Adversarial angle:** the tempting shortcut is to ship the backup code and call
it done. An untested restore is the classic false comfort — it "works" until the
day it doesn't, which is the day her data is already gone.
