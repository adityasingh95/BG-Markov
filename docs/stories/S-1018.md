# S-1018 [SAFETY] — A reported clinical time is naive local, end to end

**Epic:** 11 · **Safety story:** **Yes — ADR-8** · **Status:** ✅ Done (2026-07-30) ·
**Requirements:** REQ-004, REQ-005, REQ-010, REQ-011, ADR-8 · **Records:** DL-057 ·
**Found by:** `scripts/demo_ui.py`, the first run of the UI in a real browser

> She types **08:00**. The database stores **02:30**.
>
> And two hours later the post-meal reading does not save at all — HTTP 500, and she is
> shown *"Could not save — please try again."*

## Story
The time she reports is the time that is stored, on any phone, in any timezone — and the
post-meal reading saves.

---

## Written safety argument

### One root cause, two symptoms

`app.js`, `post_bg.js` and `corrections.js` all convert the value of a `datetime-local`
input with `new Date(iso).toISOString()`. That produces a UTC **instant** with a `Z`
suffix. Pydantic parses it into a timezone-**aware** `datetime`. Everything downstream of
the schema is naive local.

1. **The post-BG path raises.** `elapsed_min(meal.datetime, post_bg_time)` subtracts an
   aware datetime (from the request) from a naive one (read back from SQLite) →
   `TypeError` → HTTP 500 → **nothing is saved**. `/api/correction-events` fails the same
   way, at `iob_at_start_at`.
2. **The meal path does not raise. It quietly stores the wrong number.** On a phone set to
   `Asia/Kolkata`, a breakfast typed as 08:00 is persisted as 02:30.

Symptom 1 is loud and costs data. **Symptom 2 is the dangerous one.**

### Why this is an ADR-8 story and not a bug fix

ADR-8 forbids **fabricating** a clinical timestamp — `datetime.now()` standing in for a
reported time. This is worse in one specific way: it does not fabricate a timestamp, it
**relabels the one she reported**, and it does so consistently, silently, and with the
right shape. There is no anomaly to detect afterwards. A 02:30 breakfast is a plausible
row in a database belonging to someone with disordered sleep.

Worse, the corruption is **self-inconsistent inside a single row**: `meal_type` is decided
in the browser from her *local* time, so the row says `breakfast` at 02:30. Two fields
derived from the same input disagree, and nothing checks.

★ **What is at risk.** `bolus_offset_min` is sent separately and `elapsed_min` is a
difference, so both survive a uniform shift — which is precisely why this would not have
been noticed. What does **not** survive: time-of-day (meal-type consistency), alignment
against `basal_log` reported times, `iob_at_start_at` against `bolus_log`, and any join
against a profile's `effective_from` date. A shift that crosses midnight moves a meal to
the wrong **day**, and basal is constant within a day — the leakage boundary the whole
temporal-CV design rests on.

### The fix, and why it fails loud

**The wire format for a reported clinical time is a naive local wall-clock string.**
Anything carrying an offset is **rejected at the schema boundary** with a 422.

The alternatives were considered and rejected:

- **Strip the offset.** `2026-07-30T02:30:00Z` → `02:30`. Still the wrong time. Silent.
- **Convert to the server's timezone.** The server is not where she is. Silent, and wrong
  by a different amount depending on where the container runs.
- **Store the instant and a timezone.** The correct answer for a system with many users in
  many places. This system has **one** user, who reports wall-clock times off a glucometer
  and a phone. Introducing an instant/zone distinction adds a conversion at every read —
  and every conversion is a place to get it wrong in the direction that does not raise.

So: reject. `require_naive` is one named function in `core/timestamps.py`, applied by a
Pydantic validator to every reported clinical timestamp. A client that sends an offset gets
a 422 that names the field.

**It raises `ValueError`, not `SafetyViolation`.** This is a malformed input, not a breached
invariant — the same reasoning as DL-035's ICR. `SafetyViolation` means *the system tried
to do something unsafe*; a badly-formatted request means *a client sent nonsense*. Conflating
them makes the invariant vocabulary meaningless.

`core/timestamps.py` imports nothing from the project, so this does not weaken the
`core/safety.py` isolation rule by analogy.

### The client side

The three scripts stop round-tripping through `Date`. A `datetime-local` input's `.value`
is *already* a local wall-clock ISO string (`2026-07-30T11:20`) — the conversion was pure
loss. One helper, `localIso(input)`, in one place.

## Acceptance criteria

1. `require_naive` exists in `core/timestamps.py`, raises `ValueError`, names the field.
2. `MealCreate.datetime`, `MealCreate.pre_bg_time`, `PostBgUpdate.post_bg_time`,
   `CorrectionCreate.datetime`, `CorrectionFollowup.bg_after_time` all reject an aware
   datetime with 422.
3. Every form posts a naive local wall-clock string.
4. **In a browser set to `Asia/Kolkata`, a meal typed at 08:00 is stored at 08:00.**
5. The post-meal reading saves from a browser. So does a correction.
6. Nothing anywhere coerces an aware datetime into a naive one.

## TDD strategy (SDET first — written and seen to fail)

`tests/unit/test_naive_timestamps.py`
- `require_naive` accepts a naive datetime unchanged and raises on an aware one, for both a
  UTC offset and a non-UTC one (`+05:30` — the offset that actually applies here).
- **★ It raises rather than converting.** Asserting the return value is naive is not enough:
  a coercing implementation also returns a naive datetime, and returns the **wrong** one.
  The test asserts the *raise*, and a second test asserts that no code path returns a
  changed value.

`tests/integration/test_naive_clinical_times.py`
- 422 for each of the five fields, with the field named in the response.
- A naive payload still works — the regression that a blunt fix would cause.

`tests/e2e/test_timezone.py`
- **★ In a `Asia/Kolkata` context, type 08:00, assert the stored `meal.datetime` is 08:00.**
  This is the acceptance criterion and it is the one that would have caught the defect.
- The post-BG flow, from the browser, in a non-UTC timezone, asserts `post_bg` in the row.

`tests/forbidden/`
- **★ `detect_utc_roundtrip_in_client_js`** — no `toISOString()` on a value read from a
  `datetime-local` input. This is the exact line that caused it, it is the natural thing to
  write, and it will be written again.

**RED evidence:** `require_naive` does not exist; the Kolkata test stores 02:30; the
post-BG browser flow leaves `post_bg` NULL.

**Adversarial angle.** (a) **Coercing instead of rejecting** — `value.replace(tzinfo=None)`,
one character shorter than the right fix and silently wrong by the offset. (b) **Fixing only
the JS**, leaving the server happy to accept an offset from any other client. (c) **Fixing
only the schema**, leaving her unable to log at all. (d) Applying the validator to
`logged_at`, which is a system timestamp and none of this story's business.

## Outcome (BA, 2026-07-30)

**Done.** `core.timestamps.require_naive`, one `_naive(field)` validator factory in
`api/schemas.py` applied to the five reported timestamps, and `api/static/reported-time.js`
as the single place a reported time becomes a wire value. Records **DL-057**.

**Both symptoms fixed.** The post-BG 500 that silently lost her readings, and the 08:00 IST
breakfast stored at 02:30.

### Guards seen to fire, on a clean committed tree (`97d0efc`)

| Plant | Caught by |
|---|---|
| `require_naive` coerces (`value.replace(tzinfo=None)`) instead of raising | 13 tests — the unit raise test and every schema 422 |
| the UTC round trip restored in `app.js` only | all three `test_timezone.py` tests **and** the forbidden-pattern guard |

The coercion plant is the one that matters: it returns a naive datetime, satisfies
`mypy --strict`, and returns the **wrong time**. A test asserting *"the result is naive"*
passes on it. The test asserts the **raise**, so there is no result to inspect.

### One deviation from the design above
The design named only the client and the schema. `app.js`'s own `localNowIso` also had to
go: it shifted the date by `getTimezoneOffset()` before calling `toISOString()`, which is
the same bug in a disguise and additionally breaks across a DST boundary.

### Still open
- **Historical rows are not audited.** Any meal logged through a browser in a non-UTC
  timezone before today holds a shifted `datetime`. There is no marker distinguishing them,
  which is the whole problem with this class of corruption. The demo database is synthetic,
  and no real capture has happened yet, so nothing is known to be affected — but that is a
  statement about this project's stage, not a guarantee, and it should be checked before
  first real use.
