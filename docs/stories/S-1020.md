# S-1020 — Every form that posts to `/api/` actually submits

**Epic:** 11 · **Safety story:** No · **Status:** ✅ Done (2026-07-30) ·
**Requirements:** REQ-007, REQ-054, REQ-061 · **Records:** DL-059 ·
**Found by:** `scripts/demo_ui.py` — filling in the basal form and pressing Save

> ```
> {"detail":[{"type":"model_attributes_type","loc":["body"],
>  "msg":"Input should be a valid dictionary or object to extract fields from",
>  "input":"date=2026-07-30&units=26&time_taken=22%3A15"}]}
> ```
>
> That is what she sees after recording her daily Tresiba dose.

## Story
The basal form and the profile form save what she types, instead of navigating her to a raw
JSON error.

---

## What is wrong

`basal.html` and `profile.html` are plain HTML forms with
`method="post" action="/api/…"` and **no script**. A native form submit sends
`application/x-www-form-urlencoded`; the endpoints take a JSON body. FastAPI returns 422 and
the **browser navigates to it**, so she leaves the app and lands on a JSON blob.

Neither endpoint has ever been reached from a browser. Both are covered by integration
tests that post JSON directly, and both pass.

★ **Why the basal one is not cosmetic.** `effective_basal` is an EWMA over `basal_log` with
a 25 h half-life, because Tresiba takes 3–4 days to reach steady state — a forbidden-pattern
entry in its own right. Days she cannot record are days that feature is stale, and it goes
stale in a way that looks exactly like "she took the same dose again".

Profile is smaller but not nothing: ICR is what the calculator divides by.

## Acceptance criteria

1. Both forms submit JSON via `fetch` and show a toast in place, without navigating.
2. Both write their row. Asserted against the **database**, from a browser (S-1021).
3. The profile form shows the flags the endpoint already returns (DL-048 — *"a validation
   result nobody can see is not a warning"*, and until now nobody could see them).
4. **A guard: no template contains a `<form>` whose `action` starts with `/api/` without a
   script to handle it.** This is the class of defect, not the instance.

## Design

One shared `api/static/json-form.js`, not two more bespoke scripts. It reads
`data-json-form` off the form, serialises named inputs to JSON with declared types
(`data-type="number"` / `"bool"`), posts, and toasts. The bespoke handlers stay bespoke —
they do real work (draft persistence, timing validation, hypo fields) that a generic
serialiser should not try to absorb.

## TDD strategy (SDET first)

`tests/forbidden/test_native_form_post.py`
- **★ Every `<form action="/api/…">` in `api/templates/` has a `<script src=…>` in the same
  template.** Seen to fail on `basal.html` and `profile.html` before the fix. Cheap, and it
  is exactly the property that was missing.

`tests/e2e/test_basal_form.py`, `tests/e2e/test_profile_form.py`
- **★ Fill, submit, assert the row exists in the database** — and assert the browser is
  **still on the form page**, because "did not navigate" is half of what broke.
- A repeat date is a correction, not a second dose — the S-1013 rule, now reachable.
- The profile form surfaces an out-of-range flag rather than swallowing it.

**RED evidence:** the guard fails on two templates; both e2e tests navigate to a JSON body.

**Adversarial angle.** (a) **Making the endpoints accept form-encoded bodies instead.** It
would work, and it would leave her on a JSON success blob — the navigation is the other half
of the defect. (b) A guard that greps for the string `fetch` anywhere in the template
directory, which passes forever once any one file has it. (c) Letting `json-form.js` swallow
the endpoint's flags, re-opening DL-048.

## Outcome (BA, 2026-07-30)

**Done.** `api/static/json-form.js`; `basal.html`, `profile.html` and `operator_shadow.html`
declare `data-json-form`; the profile toast surfaces the endpoint's flags.
Records **DL-059**.

### ★ The guard found a third form nobody had reported
The story was written about basal and profile. The class-level guard immediately flagged the
**revoke** form on `/operator/shadow` — **the kill switch** — wired exactly the same way. It
renders only once Gate 1 is open, which is why it had never been pressed, and it is the one
control you want to work in a hurry.

That is the argument for writing the guard against the class rather than fixing the two
instances: the third one was found by the guard, in the same minute, without anyone
suspecting it.

### Guards seen to fire

| Plant | Caught by |
|---|---|
| `data-json-form` and the script removed from `basal.html` | both template guards **and** both browser flow tests |

### ★ Raised, not fixed: there is no promote control at all
`/operator/shadow` renders the *"Turn it on for her"* button `disabled` in **every** state,
because Gate 1 counts `is_promoted` among its conditions — so `gate1.is_open` is true only
*after* a promotion that no UI can perform. `POST /api/operator/promote` exists (S-1001b) and
nothing reaches it; the demo promoted by calling Python directly. Adding a promotion control
is a **safety-design decision**, not a wiring fix, and is deliberately not taken here.

### Still open
- The profile page renders the values it just changed, and does not refresh after a save —
  the old "In force now" sits next to a ✓. A reload-after-save was written and removed: it
  made the flow tests race. Cosmetic, but it is a small lie on a clinical screen.
