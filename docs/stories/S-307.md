# S-307 — Operator adherence dashboard

**Epic:** 3 (Logging & Durability) — **the last story before EPIC 3 ships** ·
**Safety story:** No · **Status:** In progress · **Requirements:** REQ-053

> Adherence is the bottleneck (`06` §1): Gate 1 needs **150 valid meals ≈ 3
> months**, and the project "ends with 40 records" if logging slips. This is the
> operator's cockpit — the two numbers that warn him *before* the data degrades:
> **days since last log** (abandonment) and **`median(logged_at − datetime)`**
> (recall bias). It is operator-only; nothing here is patient-visible (INV-2).

## Story
Give the operator (her son) a single adherence view: how much valid data exists,
how far to Gate 1, why meals are being excluded, and — the two early-warnings —
how stale the logging is and how badly transcription lag is creeping in.

## Requirement source
- **REQ-053** — operator adherence dashboard: valid-meal rate, exclusion reasons,
  **`median(logged_at − datetime)`**, days-since-last-log.
- **05b §7.1** — the mockup: `VALID MEALS n / 150 to Gate 1`, in-window rate,
  days-since-last-log, exclusions by reason, transcription-lag median.
- **03 §** — Gate 1's volume precondition is **150 valid meals** (necessary, never
  sufficient — hypo recall must still beat the baseline; that gate check is a
  later story, not this metric).

## The ★ metric — why it exists (ADR-8 payoff)
`median(logged_at − datetime)` is the whole reason `logged_at` and `datetime` are
**separate columns**. She logs at the laptop ~40 min after eating; if that lag
climbs, `bolus_offset_min` and `elapsed_min` (derived from reported times) carry
more recall error and the data silently degrades. The metric must be computed from
the **two distinct columns** — a fabricated value (always 0, or one column minus
itself) would hide exactly the degradation it exists to surface. This is the
load-bearing test.

## Design
- **`data/adherence.py`** — a pure metrics function
  `adherence_metrics(session, *, now) -> AdherenceMetrics`:
  - `valid_meals` (count `is_valid`), `meals_to_gate1 = max(0, 150 − valid_meals)`.
  - `in_window_rate` — among meals with an outcome, the share **not** excluded for
    `outside_window` (05b's "IN-WINDOW RATE"; ties to the 04 §5 ±window escape
    hatch). `None` when there are no outcomes yet.
  - `exclusions_by_reason` — count per reason across all meals.
  - `days_since_last_log` — `(now − max(logged_at)).days`; `now` is **injected**
    (the one operational clock read; not a clinical timestamp). `None` if no meals.
  - `median_lag_min` — median over meals of `(logged_at − datetime)` in minutes,
    from the two columns. `None` if no meals.
  - `GATE1_VALID_MEALS = 150` lives here with a `03 §` reference.
- **`GET /api/adherence`** — the metrics as JSON (operator).
- **`GET /operator`** — the HTML dashboard rendering them. Operator-only, not in
  the patient nav; shows **no model output** (that is shadow-mode, a later story) —
  so INV-2 is not even in play here.

## Out of scope (later stories)

- The actual Gate-1 *pass* decision (recall vs baseline) — a later gate story.

## TDD strategy (SDET, written first — seen to fail)
`tests/integration/test_adherence.py`:
- `valid_meals` / `meals_to_gate1`: 3 valid + 2 invalid, 150-target ⇒
  `valid_meals == 3`, `meals_to_gate1 == 147`.
- `exclusions_by_reason`: a meal excluded for two reasons contributes to both
  counts; a valid meal contributes to none.
- `in_window_rate`: with N outcomes and K `outside_window`, rate == `(N−K)/N`;
  `None` when no outcomes.
- `days_since_last_log`: with an injected `now`, equals whole days since the latest
  `logged_at`.
- **★ `median_lag_min` is computed from the two distinct columns:** meals whose
  `logged_at − datetime` are {10, 40, 70} min ⇒ median **40**. A guard asserts it
  is **not** 0 when the columns differ (catches "fabricated from one column").
- Empty DB ⇒ `None` metrics, `meals_to_gate1 == 150`, no crash.
- `GET /api/adherence` returns the metrics; `GET /operator` renders "150 to Gate 1"
  and the lag figure.

**RED evidence:** `data/adherence.py`, the endpoints, and `/operator` do not exist
⇒ import/HTTP failures before implementation.

**Adversarial angle:** the trap is computing the lag as `now − logged_at` or a
constant — plausible, and always wrong in the safe direction (small/zero), which
would mask the recall-bias climb the operator is supposed to catch early. The test
pins it to `logged_at − datetime`.
