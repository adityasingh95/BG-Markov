# S-403 — Exercise encoding (one-hot + duration interactions)

**Epic:** 4 (Derived Features) · **Safety story:** No (but a physiology-preserving
forbidden pattern) · **Status:** In progress · **Requirements:** REQ-024

> **Light exercise lowers BG; intense exercise can raise it (adrenaline). The
> effect is non-monotone in intensity** (`07` §5). A numeric `0/1/2` column in a
> linear model **mathematically forbids** a non-monotone effect — it forces the
> intense response to be a scalar multiple of the light one. For a patient who
> cannot feel a low, an encoding that cannot represent "intense went the other
> way" is a hazard, not a style choice.

## Story
Encode exercise as **one-hot intensity indicators + duration interactions**, so the
model can assign **opposite-signed** coefficients to light vs intense — never a
single ordinal column.

## Requirement source
- **REQ-024** — exercise intensity is one-hot encoded with duration interactions;
  **never numeric 0/1/2**.
- **`07` §5** — one-hot + duration interactions is *mandatory*; a numeric encoding
  cannot represent the physiology.
- **CLAUDE.md forbidden pattern** — "Numeric 0/1/2 exercise intensity → one-hot +
  duration interactions."

## Design
- **`features/exercise.py`** — `encode_exercise(intensity, duration_min,
  prefix="ex")` returning a feature dict:
  - `{prefix}_light`   — 1.0 if intensity is light, else 0.0
  - `{prefix}_intense` — 1.0 if intensity is intense, else 0.0
  - `{prefix}_light_min`   — duration if light, else 0.0 (duration interaction)
  - `{prefix}_intense_min` — duration if intense, else 0.0 (duration interaction)
  - `none` → all four zero (the reference level; no exercise term).
  - `intensity` is a `str` (the `ExIntensity` StrEnum value), so the encoder stays
    free of any `data`/ORM import. `prefix` lets the pipeline reuse it for both the
    in-window exercise (`ex`) and prior exercise (`pre_ex`).
- Pure function; no clock, no DB.

## Why this permits the physiology
`light/60` → `{light:1, intense:0, light_min:60, intense_min:0}`;
`intense/60` → `{light:0, intense:1, light_min:0, intense_min:60}`. These activate
**different** features, so there is **no scalar `k`** with `intense == k · light`.
A linear model can therefore fit `β_light < 0` (lowers BG) and `β_intense > 0`
(raises BG) simultaneously. A numeric `light=1, intense=2` column makes the intense
row exactly `2×` the light row — the model is forced into one sign for both, which
is the forbidden behaviour.

## TDD strategy (SDET, written first — seen to fail)
`tests/unit/test_exercise.py`:
- `none` (any duration) ⇒ all four features 0.0 (baseline).
- `light/60` ⇒ light indicator + `light_min == 60`, intense features 0.
- `intense/45` ⇒ intense indicator + `intense_min == 45`, light features 0.
- **Duration interaction:** `light/30` vs `light/60` differ only in `light_min`
  (30 vs 60) — duration actually enters the encoding.
- **★ Non-monotonicity / not-scalar-multiple:** the `light/60` and `intense/60`
  vectors are **not** scalar multiples of each other (no `k`: `intense == k·light`)
  — the property a numeric `0/1/2` column would violate. This is the load-bearing
  test: it is exactly what lets the model represent opposite-signed effects.
- `prefix="pre_ex"` produces `pre_ex_*` keys (reusable for prior exercise).

**RED evidence:** `features/exercise.py` does not exist ⇒ import error before impl.

**Adversarial angle:** the tempting shortcut is a single `exercise_intensity` column
mapping none/light/intense → 0/1/2. The not-scalar-multiple test kills it directly:
under 0/1/2 the intense vector is `2×` the light vector, so no model can send them
opposite ways — and "intense raised her BG" becomes unrepresentable.
