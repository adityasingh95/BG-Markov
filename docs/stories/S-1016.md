# S-1016 [SAFETY] — Make `POST /api/meals` actually idempotent

**Epic:** 11 · **Safety story:** **Yes — a duplicated bolus corrupts IOB, which the dose
calculator subtracts** · **Status:** In progress · **Requirements:** REQ-001, REQ-002,
REQ-006 (`05 §`) · **Records:** **DL-055** · **Rollback baseline:** `ffdc55e`

> `05 §`: *"All write endpoints are **idempotent** — the client generates a UUID per
> record."* `MealCreate.idempotency_key` is a **required** field, and a grep shows it is read
> by **nothing**. The fourth "declared and unconnected" gap, after DL-046 (`basal_log`),
> DL-049 (`actual_state`) and S-1014 (the fitted model).

## Story
A retried meal submission returns the meal that was already recorded, and creates nothing.

---

## Written safety argument

This is not a tidiness story. A duplicate meal is annoying; **a duplicate bolus is
dangerous.**

`POST /api/meals` writes a `MealEvent` **and** one or two `BolusLog` rows. `bolus_log` is
`REQ-006`'s *"sole source of truth for IOB"*. So a double-tap, a flaky connection, or an
impatient second press on a phone produces **two records of one injection**, and from that
moment:

1. **`iob_at(t)` over-reports insulin on board** — for hours, since Fiasp's curve runs ~5 h.
2. **The bolus calculator subtracts that inflated IOB** (`prescribe/bolus.py`: `... − IOB`),
   so it recommends **less insulin than she needs**, silently and plausibly.
3. **The baseline over-subtracts too** (`07 §4`), so predicted BG reads lower than reality —
   the direction that manufactures phantom hypos.
4. **`iob_at_meal` is a model feature**, so the corruption is learned rather than noticed.

Every one of those is quiet. There is no error, no flag, and no screen on which a doubled
bolus looks different from a real one. The system is designed to make failure *loud*, and
this one is currently inaudible.

**Why an invariant is not the answer.** There is no safe universal rule saying "two boluses
close together is wrong" — she genuinely does take a correction shortly after a meal bolus.
The defect is not "two boluses exist"; it is "**one submission produced two records**". That
is an identity problem, and it is fixed with identity, not with a threshold.

---

## Design

### `meal_event.idempotency_key` — a **UNIQUE** column, nullable
- **Unique at the database, not checked in Python.** A read-then-insert has a race: two
  submissions can both find nothing and both insert. On her single-user laptop that race is
  unlikely — but "unlikely" is what the double-tap already was, and a constraint costs
  nothing. The DB is the arbiter.
- **Nullable**, because every meal recorded before this story has no key. Backfilling
  invented keys would fabricate provenance for rows that never had it.

### The route: look up first, insert inside a `try`, catch the constraint
```
existing = by_key(...)         → return it, create nothing
else: insert (meal + boluses)  → on IntegrityError, re-read and return the winner
```
The second branch is what makes it correct under a race rather than merely usually correct.

**A repeat returns `200` with the SAME `meal_id`** — not `409`. A retry is not an error: from
her side she pressed the button twice and there is one meal, which is exactly what she meant.
A 409 on a flaky connection would tell her the log failed when it succeeded, and she would
enter it again.

### ★ Same key, different data ⇒ the **first** record wins, unchanged
The stored meal is returned as-is and nothing is updated. A key identifies *a submission*,
not *a slot to overwrite*. Silently updating a clinical record because a retry carried
different numbers would be an unaudited edit to a clinical record — which `04 §10` forbids —
and the retry is far more likely to be a stale form than a considered correction. Corrections
have their own audited path.

---

## TDD strategy (SDET first — written and seen to fail)

`tests/safety/test_meal_idempotency.py`:
- **★ THE ONE THAT MATTERS: a repeat submit creates NO second bolus.** Assert the
  `bolus_log` count, not only the meal count. A meal-only assertion passes for an
  implementation that dedupes the meal and re-inserts the boluses — which is the whole harm.
- **★ IOB is unchanged after the retry** — asserted through `iob_at_start_at`, i.e. the
  quantity the calculator actually consumes, not the row count that implies it.
- **★ …and so is the recommended dose.** The end of the causal chain, asserted directly:
  same inputs before and after a retry ⇒ the same suggested units.
- A repeat returns `200` and the **same `meal_id`**.
- **★ Same key, different carbs ⇒ the stored meal is unchanged** and nothing is audited.
- Two **different** keys with identical data ⇒ two meals. Deduping on content would silently
  drop a real second meal.
- **★ A concurrent double-insert resolves to one row** — the unique constraint is exercised
  directly, not just the happy-path lookup.
- Meals recorded before this story (`idempotency_key IS NULL`) are untouched, and **several
  NULLs coexist** — a naive `UNIQUE` that rejects a second NULL would break every historical
  row.

**RED evidence:** `meal_event.idempotency_key` does not exist; two identical POSTs create two
meals and two boluses.

**Adversarial angle.** Four. (a) **Dedupe the meal, re-insert the boluses** — passes a
meal-count test and preserves the entire harm. (b) **Check-then-insert with no constraint**,
correct until it isn't. (c) **Update the existing row** with the retry's data — an unaudited
edit to a clinical record. (d) **Return 409**, which tells her a successful log failed and
invites her to log it a third time.
