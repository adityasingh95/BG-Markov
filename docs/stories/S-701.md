# S-701 [SAFETY] — ★ Temporal cross-validation runner

**Epic:** 7 (Validation) — **opens EPIC 7** · **Safety story:** Yes (leakage is the
central validation hazard) · **Status:** In progress · **Requirements:** REQ-034

> **The most likely way this project fails is a model that looks brilliant on
> retrospective data, gets trusted, and is quietly wrong about a low.** The single
> largest cause of "looks brilliant" is leakage: basal is constant within a day and
> days autocorrelate, so if any part of a day lands in both train and test, the model
> is scored on information it effectively already saw. S-404 gave us the *fold
> primitive*; S-701 gives us the **runner that drives the actual model across those
> folds** — and, adversarially, **re-checks the temporal invariants at fit time on
> every fold it is handed**, because a future refactor will try to feed it a leaky
> split.

## Story
Provide a temporal cross-validation runner that: takes the feature matrix, states, and
per-row datetimes; builds forward-chaining folds; **re-asserts on every fold that
`max(train.datetime) < min(test.datetime)` and that no calendar day appears in both
train and test** (raising on violation); fits the feature scaler on the **train fold
only**; and drives a model-agnostic `fit_predict` to produce **out-of-sample**
predictions for the metric suite (S-702). Random/shuffled splitting is impossible by
construction and `shuffle=True` appears nowhere (existing forbidden guard).

## Requirement source
- **REQ-034 / 07 §9 — Splitting.** *Forward-chaining temporal CV. NEVER random. Basal
  is constant within a day and days are autocorrelated — a random split leaks day-level
  information into test. No `date` may appear in both train and test in any fold.*
- **09 §7 (leakage) / CLAUDE.md** — leakage tests are adversarial: *assume a future
  refactor will try to weaken them, and write the test that catches it.*

## Design
`models/validation.py` (`models/` may import `features/`; the runner orchestrates a
model fit, so it lives above the feature layer). Imports no `core` — a leakage failure
is a validation-integrity error, not one of INV-1..9:

- **`TemporalLeakageError(Exception)`** — raised when a fold violates temporal order or
  day-disjointness.
- **`assert_temporal_split(dates, train_idx, test_idx) -> None`** — the guard, usable
  standalone: raises on an empty side, on any day shared between train and test, or when
  `max(train) ≥ min(test)`.
- **`temporal_cv(x, y, dates, fit_predict, *, n_splits=3, scale=True, folds=None) ->
  TemporalCVResult`** — for each fold: **re-assert the split** (defense in depth, even
  when `folds` were generated internally), fit `make_scaler()` on the **train rows
  only** and transform train+test with it, then call
  `fit_predict(x_train, y_train, x_test)` and keep the test predictions. `folds` may be
  injected (so an adversarial test can hand it a leaky split and prove it raises).
- **`TemporalCVResult`** / **`FoldPrediction`** — per-fold train/test indices,
  out-of-sample predictions and truth; `oos_predictions()` / `oos_truth()` concatenate
  across folds for S-702.

**Model-agnostic.** `fit_predict(x_train, y_train, x_test)` lets the same runner drive
the baseline, the ordinal model, or the Bayesian ordinal. The end-to-end test drives the
**real** `fit_ordinal` → `predict_proba`, proving the harness produces genuine
out-of-sample probabilities against the actual model (the auditor's requirement).

## Written safety argument (why leakage cannot pass) [SAFETY]
1. **Ordering is re-checked, not assumed.** Even though `forward_chaining_folds`
   constructs ordered, day-disjoint folds, `temporal_cv` calls `assert_temporal_split`
   on **every fold before fitting**. If a later change swaps in a different (leaky) fold
   source — a random split, a stratified split, anything with a shared day — the runner
   raises `TemporalLeakageError` instead of silently producing an optimistic score.
2. **Day-level, not row-level.** The guard compares calendar **days**, not timestamps,
   because basal is constant within a day — two meals from the same day on opposite
   sides of the split is the exact leak REQ-034 names, and the check catches it even
   when the timestamps differ.
3. **The scaler never sees the test fold.** `make_scaler()` is fit on train rows only
   and then applied to test rows; a test-fold outlier cannot shift the centering the
   model trains against. A test proves a giant test-fold value leaves the train-fold
   transform unchanged.
4. **Random splitting is unreachable.** No `shuffle` parameter exists on any path here,
   and the forbidden-pattern guard fails the build on `shuffle=True` anywhere in the
   tree. There is no code path that produces a random split.

## TDD strategy (SDET, written first — seen to fail)
`tests/leakage/test_temporal_cv.py`:
- **Runner folds are ordered & day-disjoint.** Driving `temporal_cv` over meals on
  distinct days yields out-of-sample predictions for every test row, no raise; each
  fold satisfies `max(train) < min(test)` and disjoint day-sets.
- **★ A leaky fold raises.** Hand `temporal_cv` (and `assert_temporal_split`) a fold
  with a day in **both** train and test → `TemporalLeakageError`; likewise a fold where
  `max(train) ≥ min(test)`.
- **★ A random/shuffled split is rejected.** A shuffled index split (days interleaved
  across train/test) raises — the "looks brilliant, is useless" path is blocked.
- **Scaler is train-only in the runner.** A giant outlier in the test fold does not move
  the train-fold centering the model is fit on.
- **★ Runs against the real ordinal fit.** `temporal_cv` with
  `fit_predict = fit_ordinal(...).predict_proba` returns out-of-sample probabilities for
  every test row, each row summing to 1 — the harness works against the actual model.
- **`shuffle=True` absent** from `models/validation.py` and `features/cv.py` (the
  forbidden AST guard already enforces this tree-wide; re-checked here for S-701).

**RED evidence:** `models/validation.py` does not exist ⇒ import error before impl.

**Adversarial angle:** the trap is to "improve" CV later by reaching for
`sklearn`'s `KFold`/`train_test_split` (random by default) or by generating folds
somewhere that does not guarantee day-disjointness — and to celebrate the resulting
high score. The leaky-fold and shuffled-split tests are the tripwires: any fold that
shares a day, or is not strictly time-ordered, makes the runner **raise** rather than
score, so an optimistic number can never be produced from a leaky split.
