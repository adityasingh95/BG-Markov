# S-306 — Correction-only event capture

**Epic:** 3 (Logging & Durability) · **Safety story:** No (but feeds the most
safety-critical number) · **Status:** In progress
**Requirements:** REQ-013 · **Feeds:** ISF derivation (`07` §6), Gate 2.

> **The highest-value data the system collects.** A correction bolus taken with
> **no food** is the only causally *unconfounded* read on ISF — nothing to confound
> the (bg_before − bg_after)/units signal. ISF is "the most dangerous number in the
> system" (`07` §2): too low → over-dosing → a low she cannot feel. Every clean
> correction event moves ISF off the population default and toward her real value.

## Story
Capture a standalone correction (a correction bolus with no meal), prompt for the
**+4 h follow-up BG** so the drop can be measured, and store the event so the
future ISF-derivation (`07` §6) has clean data to work from.

## Requirement source
- **REQ-013** — correction-only events (no food) are captured with a +4 h
  follow-up reading.
- **F-3.2** — when a correction bolus is logged with no meal, ask "will you be
  eating in the next 4 hours?"; if no, prompt a +4 h BG and show the alarm time.
  Capture `bg_before`, `units`, `bg_after`, `food_in_window`, computed
  `iob_at_start`. She should be actively encouraged to log these.
- **`07` §6** — `derived_ISF = mean((bg_before − bg_after)/units)` over events
  with `iob_at_start < 0.5 AND food_in_window == False`; ≥5 clean events before it
  may override the default; never silently swapped.

## The iob_at_start deferral (decision)
`iob_at_start` requires the IOB engine — `iob_at(timestamp)` over `bolus_log`,
the Fiasp exponential curve — which is **S-401 (EPIC 4, post-ship)** and does not
exist yet. CLAUDE.md forbids hand-entered IOB (it must be derived) and forbids
working around a missing piece. Per the operator's decision, S-306 **defers**
`iob_at_start`: the event is captured now with `iob_at_start = NULL`, to be
**backfilled by S-401's `iob_at()`**. The `07` §6 clean-signal filter already
requires `iob_at_start < 0.5`, so an event with a NULL IOB is simply **not yet
clean** — it cannot enter ISF derivation until the IOB is known. This is loud by
construction (a NULL never satisfies `< 0.5`), never a silent inclusion. Recorded
in the decision log; `correction_event.{iob_at_start, bg_after, bg_after_time}`
become nullable (two-phase capture + deferred IOB).

## Design
- **Two-phase capture**, mirroring the meal → post-bg pattern:
  - `POST /api/correction-events` — `{datetime (reported), bg_before, units,
    food_in_window}`. Writes the **correction bolus to `bolus_log`** (REQ-006 —
    every injection is logged, so S-401's IOB can see it) and the event row
    (`iob_at_start`/`bg_after`/`bg_after_time` NULL). If `food_in_window == False`,
    the response prompts a +4 h follow-up with the alarm time (`datetime + 4 h`).
  - `PATCH /api/correction-events/{id}/followup` — `{bg_after, bg_after_time
    (reported), food_in_window}`. Stores the +4 h reading and confirms
    `food_in_window`.
- **ADR-8 throughout:** `datetime` and `bg_after_time` are **reported**; only
  `logged_at` is the system clock. No `now()` touches a clinical timestamp.
- **`get_clean_correction_events`** (`data/repositories.py`) — the `07` §6
  clean-signal filter: `food_in_window == False AND iob_at_start is not None AND
  iob_at_start < 0.5`. This is the accessor the future `derive-isf` (S-501) reads.
  It is where the ★ exclusion lives.
- **Accessible `/corrections` form** — a "log a correction (no food)" entry with
  reported time, BG, units, and the "eating in the next 4 h?" question; ≥18 px,
  48 px targets, `inputmode=numeric` on BG/units (05b §2). No patient-visible model
  output (INV-2 holds — nothing here predicts anything).

## Out of scope (later stories)
- The actual ISF **regression** and `implied_isf`/`clean_events_count` response
  fields (`05` §3) — that is the derivation, **S-501** (`cli derive-isf`).
- `iob_at_start` **computation** — **S-401** backfills it.

## TDD strategy (SDET, written first — seen to fail)
`tests/integration/test_correction_events.py`:
- `POST /api/correction-events` persists the event, writes a **correction**
  `bolus_log` row (REQ-006), and — when `food_in_window == False` — returns a +4 h
  prompt whose alarm time is **reported `datetime` + 4 h** (never `logged_at`+4 h).
- `food_in_window == True` on create ⇒ **no** +4 h prompt (confounded; not an ISF
  signal).
- `PATCH …/followup` stores `bg_after` + reported `bg_after_time`.
- **★ `get_clean_correction_events` excludes `food_in_window == True`** and
  excludes events whose `iob_at_start` is unknown (NULL) — the deferral must not
  silently admit a possibly-confounded event. A `food_in_window == False,
  iob_at_start = 0.2` event **is** returned.
- 404 on follow-up for an unknown event.

`tests/integration/test_correction_schema.py`:
- `correction_event.{iob_at_start, bg_after, bg_after_time}` are **nullable**; the
  Alembic migration head applies the change (an event row persists with those NULL).

`tests/safety/test_reported_timestamps.py` (extend): a correction event's
`datetime` and `bg_after_time` are the reported values, never `now()`.

`tests/a11y/test_corrections_form.py`: axe clean on `/corrections`; BG/units fields
`inputmode=numeric`; base font ≥ 18 px.

**RED evidence:** the endpoints, `record_correction_event`,
`get_clean_correction_events`, the nullable columns, and `/corrections` do not
exist ⇒ import/HTTP/attribute failures before implementation.

**Adversarial angle:** the trap is treating a NULL `iob_at_start` as "fine, no IOB"
and admitting the event to ISF derivation. A NULL means *we do not yet know* the
confounder — the clean-events filter must exclude it, or the deferral would quietly
poison the most dangerous number in the system.
