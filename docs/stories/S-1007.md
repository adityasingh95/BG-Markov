# S-1007 [SAFETY] — Gate-1 shadow-period precondition

**Epic:** 10 · **Safety story:** Yes — it **tightens** INV-2 · **Status:** In progress ·
**Requirements:** **REQ-048**, INV-2 · **Record:** DL-034 (gap G2) · **Closes the last
code-vs-spec divergence in `03 §3`** · **Rollback baseline:** `7a7c3bf`

> **REQ-048 has existed since the PRD and is enforced nowhere.** *"Shadow mode ≥ 90 days before
> patient-visible output."* `03 §3` lists it as a Gate-1 condition. No code reads it, and no test
> covers it — a requirement with no covering test is a visible gap by this project's own rule.
> This story gives REQ-048 its first enforcement and its first test.

## Story
Gate 1 additionally requires **≥ 90 days of shadow-mode operation**, measured from the first
logged prediction to now, before it can open.

## Design

### `data/repositories.py::shadow_days(session, *, now) -> int`
- Computed from **`prediction_log.created_at`** — the earliest logged prediction to `now`.
- **Never a stored boolean.** A stored flag can be set once and then lie forever; a derived
  count cannot. If predictions stop, the clock keeps reflecting reality rather than a past claim.
- **`now` is injected**, not read from the wall clock inside the function. Two reasons: the
  project has exactly one sanctioned clock reader (`core/clock.py`, ADR-8), and an injected
  `now` makes "day 89 vs day 90" testable without waiting three months.
- **Fails closed:** no predictions ⇒ `0`. A negative interval (clock skew, a row dated in the
  future) is **clamped to 0**, never allowed to appear as elapsed time.

### `prescribe/gates.py`
- **`SHADOW_MIN_DAYS = 90`** — a named constant with REQ-048 in its comment, so the number is
  traceable to the requirement rather than looking like a team choice.
- `gate1_status(..., shadow_days: int)` — **required**, same reasoning as `is_promoted` (S-1006):
  a default would let a call site omit the question and still compile.
- `Gate1Status` gains `shadow_days` and `meets_shadow_period` so the operator dashboard can
  render the countdown (*"day 61 of 90 — 29 to go"*) rather than a bare "blocked".
- **`gates.py` stays DB-free.** It imports only `core.safety` today and keeps that shape: the
  gate is a pure function of live inputs, the caller reads them fresh. That is what makes
  "never cached" (ADR-7) structurally true rather than a convention.

## Written safety argument [SAFETY]

**What the 90 days are actually for.** Not ceremony. A model can look excellent on a
retrospective split and be wrong prospectively — the failure this whole project is built around.
Ninety days of *predicting before knowing* is the only evidence that distinguishes the two. Gate
1 without it would rest on exactly the retrospective performance CLAUDE.md warns is "almost
always leakage."

**Why derived, never stored.** A boolean `shadow_complete` would be set once by whoever ran the
migration or the backfill, and would then be true forever regardless of what the data said. A
count derived from `prediction_log` is re-answered on every call and cannot drift from reality.
This is the same principle as ADR-7's "gates are evaluated live, never cached."

**Why clamped at zero.** A clock that steps backwards, or a row written with a future timestamp,
would otherwise produce a negative or wildly large elapsed time. Every ambiguity resolves toward
*not yet* — the gate stays shut.

**Why the constant is named and traced.** `90` appearing as a literal inside a condition invites
a future reader to tune it. `SHADOW_MIN_DAYS`, commented with REQ-048, makes it clear that
changing it is changing a requirement — which is an escalation, not a code change.

**What this does not do.** It does not make Gate 1 open. Ninety days is a *precondition* joining
volume, beats-baseline, and manual promotion (S-1006). All four must hold. Time passing is never
evidence of quality.

## TDD strategy (SDET first — written and seen to fail)
`tests/safety/test_gates.py`:
- **★ 89 days, everything else ✓ ⇒ CLOSED; 90 days ⇒ open.** The boundary, exactly.
- **★ Long shadow never substitutes for the others:** 500 days but 149 meals ⇒ closed; 500 days
  but recall ≤ baseline ⇒ closed; 500 days but not promoted ⇒ closed. **Time is not evidence.**
- **`shadow_days` is required** — omitting it raises `TypeError`.
- `Gate1Status` exposes `shadow_days` + `meets_shadow_period` for the countdown.

`tests/integration/test_shadow_clock.py`:
- **★ No predictions ⇒ 0** (fails closed — the state on day one).
- Computed from the **earliest** `created_at`, not the latest and not the count of rows.
- **★ A clock that steps backwards ⇒ 0, never negative.**
- A future-dated row does not manufacture elapsed time.
- **★ Not a stored flag:** the same session yields a *larger* count when `now` advances, proving
  it is re-derived per call rather than memoised.

**RED evidence:** `shadow_days` does not exist; `gate1_status` takes four arguments.

**Adversarial angle.** Two temptations. (a) Storing a `shadow_complete` boolean "for speed" — it
would be set once and then lie forever, and nothing in a green build would reveal it. (b)
Reading the wall clock inside `shadow_days` — convenient, but it makes the 89/90 boundary
untestable without waiting a quarter, and it puts a second clock reader in a codebase that
deliberately has one.
