# S-1001b [SAFETY] — The promotion control

**Epic:** 10 · **Safety story:** Yes — it is the **only door Gate 1 has** · **Status:** ✅ Done (2026-07-18) · **Requirements:** REQ-058, INV-2 · **Records:** DL-044 (the split) ·
**Rollback baseline:** `7a7c3bf`

> `05 §6`: *"`POST /api/operator/promote` — **[SAFETY]** Open Gate 1. Manual only."*
> `data/promotion.py` has existed since S-1006 and nothing reachable calls it. This story
> gives it its one caller, and makes that caller refuse.

## Story
The operator can open Gate 1 — deliberately, once every automatic condition already holds,
with the reason for any refusal visible — and can revoke it at any time.

## ★ The subtlety that shapes the whole design

Gate 1 has five conditions and **`is_promoted` is one of them**. So the promote endpoint
**cannot** gate on `gate1_status(...).is_open`: before promotion that is false *by
definition*, and the check would refuse every promotion forever, including the correct one.

The precondition is therefore the **other four** — volume, beats-baseline, honest
percentages, ninety shadow days. `Gate1Status` gains a computed
`automatic_conditions_met` for exactly this, named so nobody later "fixes" the endpoint by
substituting `is_open` and silently bricks the only door the gate has.

This is the kind of mistake that produces a *safe-looking* failure — a gate that can never
open is not obviously a bug — and would be found months later by someone with a good model
and no way to ship it.

## Design

### `prescribe/gates.py`
- `Gate1Status.automatic_conditions_met` — a **property**, not a stored field, so it cannot
  drift from the four booleans it summarises.
- `Gate1Status.failed_conditions` — the machine-readable names of what is unmet, so the 409
  body and the UI say the same thing rather than two hand-maintained lists.
- Still DB-free, still model-free.

### `POST /api/operator/promote`
```json
{ "model_version": "v3-2026-07-01", "confirmed": true }
```
- **The server re-evaluates the gate from live data.** It trusts nothing the client sends
  about readiness. A button enabled in a browser is not permission; the browser is the one
  part of this system a future bug is most likely to reach.
- **`409 PRECONDITIONS_NOT_MET`** naming *every* failed condition, not just the first — the
  operator should see the whole distance, not discover it one refusal at a time.
- **`confirmed: true` is required** (`400 CONFIRMATION_REQUIRED`). Reaching the URL is not
  a decision; saying yes is.
- **`404`** on an unknown version, creating nothing.
- Audited by `data/promotion.py` (who, when, old→new), which also demotes the incumbent in
  the same transaction.

### `POST /api/operator/revoke`
- **No preconditions. Ever.** A gate you cannot shut is not a gate. Revocation works whether
  or not the conditions still hold — indeed *especially* when they no longer do.
- Takes effect on the next call (gates are live, ADR-7).

### The control on `/operator/shadow`
- Sits **below** the evidence, not above it: the decision follows the reading.
- **Disabled while any condition is unmet, with the reason always visible** (`05b §7.3`) —
  never a dead control with no explanation, which invites hunting for a way round it.
- Copy states plainly that good numbers are not permission.

## Written safety argument [SAFETY]

**Why this endpoint exists at all.** INV-2 says no patient-visible model output before
Gate 1. S-1006 made promotion a required Gate-1 condition, and `data/promotion.py` the only
writer. But nothing could *call* it — so in practice Gate 1 could never open, and the
manual-promotion requirement was untested as a workflow. An unopenable gate is not safety;
it is an unfinished feature that happens to look safe.

**Why the server re-checks.** The UI already knows the conditions and disables the button.
That is a courtesy, not a control. Anything that reaches this URL — a stale tab, a
half-finished script, a future bug — must meet the same bar. The check lives at the point
of effect.

**Why every failed condition, not the first.** A refusal that reveals one blocker at a time
teaches the operator to treat the gate as an obstacle course. Showing the whole list makes
it read as what it is: a description of what is not yet true.

**Why `confirmed: true`.** Separating *reaching* the action from *taking* it. The
difference matters when the action is putting someone who cannot feel a low in front of a
model.

**Why revoke is unconditional.** The failure this system is built around is a model that
looks good, gets trusted, and is quietly wrong. The response to suspicion must never be
blocked by a precondition check — including the check that the model still looks fine.

**What this does not do.** It does not make the model good, and it does not lower any bar.
It adds a door to a wall that already stands, and the door only opens from the inside, by
hand.

**Deferred, deliberately:** whether a tripped kill switch should also block promotion.
`03 §4` does not say, and inventing the rule here would be exactly the sort of unsanctioned
tightening BA is supposed to flag rather than commit. Raised as an open item; the kill
switch already suppresses ML output independently, so nothing is unguarded meanwhile.

## TDD strategy (SDET first — written and seen to fail)
`tests/safety/test_promotion_api.py`:
- **★ The unsatisfiable-precondition trap:** with all four automatic conditions met and
  `is_promoted` false, promotion **succeeds**. If the endpoint ever gates on `is_open` this
  fails, and it is the only thing that would notice.
- **★ Each of the four automatic conditions, unmet alone ⇒ 409**, with that condition named
  in the body.
- **★ Several unmet ⇒ all of them named**, not just the first.
- **★ No `confirmed` / `confirmed: false` ⇒ 400 and nothing is promoted.**
- Unknown version ⇒ 404, creating nothing and promoting nothing.
- **★ Promotion is audited** — the `audit_log` row exists with old→new and who.
- **★ Revoke works with preconditions unmet** — a gate you cannot shut is not a gate.
- Revoke takes effect on the next read (ADR-7), and is audited.
- **★ No query param, header or env var promotes** without meeting the conditions.
- **★ AST: nothing under `cli/` calls `promote_model`.** The "refit then promote" cron job
  is the exact thing `07 §Retraining` forbids, and it is one line to write.

`tests/integration/test_operator_shadow.py` (extended):
- The button renders **disabled** with the unmet reasons visible when the gate is not ready.
- It renders **enabled** when all four automatic conditions hold.

**RED evidence:** `POST /api/operator/promote` 404s;
`Gate1Status.automatic_conditions_met` does not exist.

**Adversarial angle.** Three. (a) Gating the endpoint on `is_open` — plausible, tidy,
and it permanently bricks the gate in a way that looks like caution. (b) Trusting a
client-supplied "ready" flag because the UI already computed it. (c) Adding preconditions
to *revoke* for symmetry, which would mean the one time you most need to shut the gate is
the one time you cannot.

## Outcome (BA, 2026-07-18)

**Done.** `Gate1Status.automatic_conditions_met` / `.failed_conditions`,
`POST /api/operator/promote`, `POST /api/operator/revoke`, and the control on
`/operator/shadow`. 566 tests green, 99.61% coverage, `ruff` and `mypy --strict` clean.
Commits: `c280bc4` (BA) → `1201f50` (SDET RED) → `7606872` (Dev GREEN), SDET fix `22b565d`.

**Gate 1 now has a door, and the door refuses.** Before this, `data/promotion.py` existed
and nothing reachable called it: Gate 1 could not open at all, and the manual-promotion
requirement had never been exercised as a workflow. That is not safety — it is an
unfinished feature that happens to look safe.

**The `is_open` trap is real, and the plant proved it.** Substituting `is_open` for
`automatic_conditions_met` in the endpoint breaks **7 tests** — but every one of those
failures is *"promotion was refused"*, which in a thinner suite would read as the gate
working. The test that makes it unambiguous is
`test_promotion_succeeds_when_the_four_automatic_conditions_hold`, written for exactly this.

**Guards seen to fire, then reverted.**
- `is_open` substituted for `automatic_conditions_met` ⇒ 7 fail (the gate is bricked).
- Preconditions added to **revoke** "for symmetry" ⇒ 1 fails — the one that promotes, lets
  the model go bad, and then needs to shut the gate.
- The 409 truncated to the first failed condition ⇒ 1 fails.
- A `_refit_and_ship()` planted in `cli/` calling `promote_model` ⇒ the AST guard fires.
  That is the "refit then promote" cron job `07 §Retraining` forbids, and it is one line.

**One SDET defect.** The meal fixture wrote `net_carbs_g`, which is a generated column
(`04 §4`), so nine tests failed on an `OperationalError` instead of on their assertions —
noise that hides whether the endpoint is right. Fixed in a separate SDET commit.

**Deviations from the design above:** one, deliberate. `PromotionRequest` **ignores**
unknown fields rather than rejecting them. The story implied rejection; ignoring is the
stronger statement, because it makes a client's readiness claim provably *inert* rather
than merely unwelcome — and the test asserts the request still gets a 409, not a 422.

**Still deferred:** whether a tripped kill switch should block promotion (`03 §4` is silent;
inventing the rule here would be unsanctioned tightening). The kill switch suppresses ML
output independently, so nothing is unguarded meanwhile.

**Gate 1 is still closed.** Nothing has been promoted, and on today's data nothing could be.
