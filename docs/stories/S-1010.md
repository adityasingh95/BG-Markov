# S-1010 — Patient-profile update surface

**Epic:** 10 · **Safety story:** No — but it is the only writer of the numbers the dose
calculator divides by · **Status:** In progress · **Requirements:** REQ-061, REQ-054 ·
**Records:** **DL-048** (the validation policy) · **Rollback baseline:** `7a7c3bf`

> Clinical constants have been versioned since S-201 (REQ-054) and **there is no action
> that appends a version.** Today the only way to set the ICR is editing the database by
> hand — which is why the calculator built in S-1003 renders *"setting missing"* and
> nothing in the app can change that.

## Story
The operator records a revised ICR / ISF / target as a **new version**, keeping the old
one, and the calculator picks it up on the next call.

## Design

### `data/profile.py::append_profile_version(session, *, effective_from, icr, isf, target_bg, changed_by)`
- **Appends. Never mutates.** REQ-054 — *"version every change, never overwrite."* The
  previous row is left exactly as it was, because a dose computed last March was computed
  with last March's numbers and the record has to still say so.
- **Refuses `icr <= 0` / `isf <= 0`** (DL-048). The calculator divides by both; there is no
  meaningful behaviour to fall back on, so this is an input error at the door rather than a
  `ValueError` three layers down.
- Audited to `audit_log` (old → new, per field), like promotion.

### Flagging, not blocking — two kinds, and only one is a clinical range
1. **Outside the documented expected range.** `04 §1` gives **ICR 7–10**. That band is
   *traced to the spec*, not chosen here.
2. **A large change from her own current value** — a factor of 2 or more in either
   direction. This catches the decimal-point typo (`9` → `90`, `30` → `300`) **without
   inventing a clinical range for ISF**, which `04 §1` does not give one for. It is a
   typo-detection heuristic on relative change, derived from her own history; it is a
   *display* rule and it never blocks.

**Neither blocks.** Per DL-048: hard limits would push a genuine out-of-range clinical
change into a hand-edit of the database, which is audited nowhere and versioned by nobody —
the safer-looking option produces the less safe outcome.

### `POST /api/operator/profile` + `GET /operator/profile`
`05 §6` names the endpoint. The screen shows the **current values**, the **history**, and —
on submit — the new value beside the old one with any flags stated in words.

## Why this is not a `[SAFETY]` story but is close to one

It writes no dose and evaluates no gate. But **every number it writes is divided by, in the
one place the system suggests insulin.** The safety properties that matter are already
enforced downstream and stay there: INV-3 caps and flags the result, INV-4 refuses below
BG 80, and `recommend_bolus` raises on a non-positive ICR regardless of what this screen
allowed. This story adds a door; it does not move a wall.

## TDD strategy (SDET first — written and seen to fail)
`tests/integration/test_profile_update.py`:
- **★ Appending leaves the old row intact** — both versions present, the old one unchanged
  field-for-field (REQ-054). The natural implementation is an `UPDATE`, and it would pass a
  "the calculator sees the new value" test perfectly.
- **★ The calculator reflects the new value on the next call, not a cached one** — change
  the ICR, recompute, get a different dose in the same session (ADR-7 in spirit).
- **★ `active_profile` picks the latest `effective_from`**, tie-broken on `profile_id`, not
  insertion order.
- `icr <= 0` and `isf <= 0` are refused, and **nothing is written** when they are.
- **★ Out-of-range is flagged and still written** — ICR 20 lands, with a flag. Blocking it
  would send the change to a hand-edit that nobody audits.
- **★ A 10× typo is flagged even where no clinical range is documented** — ISF 30 → 300
  flags on relative change, which is what catches a misplaced decimal point.
- A normal change (9 → 8.5) is written with **no** flag — a screen that warns about
  everything warns about nothing.
- Every change is **audited**, per field, old → new.
- The screen renders current values, history, and the flags in **words**.

**RED evidence:** `data.profile` does not exist; `POST /api/operator/profile` 404s.

**Adversarial angle.** Two. (a) An `UPDATE` instead of an `INSERT` — smaller, obvious, and
it destroys the only record of what the calculator was actually using last month. (b)
Blocking out-of-range values because it feels safer, which moves the change to a
hand-edit of the database and out of the audit log entirely.
