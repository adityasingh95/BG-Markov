# S-1021 — The browser suite grades outcomes, not the presence of a message

**Epic:** 11 · **Safety story:** No (but it is what makes S-1018 catchable) · **Status:** ✅ Done (2026-07-30) ·
**Requirements:** REQ-001, REQ-010, REQ-011 · **Records:** DL-056

> ```python
> toast = page.locator("#toast")
> toast.wait_for(state="visible", timeout=5000)
> assert (toast.text_content() or "").strip(), "expected a save confirmation"
> ```
>
> That is `tests/e2e/test_post_bg_form_asks_reported_time_and_saves`, and it has been
> green since S-303. The toast it was passing on read
> **"Could not save — please try again."**

## Story
The end-to-end suite asserts that a save **happened**, not that a message **appeared**, so
a broken write surfaces as a red test instead of a green one.

---

## Why this is its own story

A browser suite already existed. It drove real Chromium, it ran in CI, and it covered the
exact form that was broken. It did not fail, because its assertion could not tell success
from failure: **any** non-empty toast satisfied it, and the failure path also writes a
toast — that is what a good error state does.

The test name says `_and_saves`. Nothing in it looks at whether anything saved.

★ **The lesson generalises past this one line.** A UI test that asserts on the *existence*
of feedback is testing that the page has a `#toast` element. It is worth roughly that much.
The assertion has to reach the thing the user actually wanted: a row in the database.

## Acceptance criteria

1. Every e2e flow that submits a form asserts a **success** outcome, via one shared helper,
   and the helper fails on the real failure copy.
2. `assert_saved` is proven to fire: a test feeds it the failure toast and expects it to
   raise. A guard nobody has watched fail is not a guard.
3. The e2e fixtures expose a **database session** so a flow test can assert on rows, not
   only on rendered text.
4. Flows covered end to end in a browser: meal log, post-BG, correction, basal, profile,
   the double tap, and a non-UTC browser timezone.
5. `pytest -m e2e` is green on a clean tree once S-1018/S-1019/S-1020 land, and each of
   those three stories has at least one e2e test that fails before its fix.

---

## Design

### `tests/e2e/conftest.py`
- `assert_saved(page)` — waits for the toast, then asserts it is **not** any known failure
  copy and does match a success marker. One place, so a future flow cannot quietly opt out.
- `db_session` — a session against the same SQLite file the live server is serving, so a
  test can count rows after a click.
- `browser_at(timezone_id)` — a context factory, because "the phone is in India" is a real
  configuration and not an exotic one.

### What this story does **not** do
It does not fix the three defects. It makes them visible. The fixes are S-1018, S-1019 and
S-1020, and each of them is expected to arrive with this suite already red for it.

---

## TDD strategy (SDET)

- **★ `assert_saved` raises on `"Could not save — please try again."`** — the assertion that
  the assertion works. Written first, and seen to fail while `assert_saved` did not exist.
- **★ The post-BG flow asserts `post_bg` is in the database**, not that a toast appeared.
  RED until S-1018.
- The meal flow asserts a `meal_event` row with the **typed** reported time.
- A test that the failure copy in `post_bg.js`, `app.js` and `corrections.js` is exactly the
  string `assert_saved` rejects — otherwise the helper drifts out of sync with the page and
  silently stops rejecting anything.

**Adversarial angle.** (a) Weakening `assert_saved` to `"could not" not in toast` — passes on
a blank toast. (b) Asserting on the toast *and* the row, but with the row read from a
different database than the server writes to — the a11y fixture bug (S-102) in a new place.
(c) Making `assert_saved` accept an empty toast.

## Outcome (BA, 2026-07-30)

**Done.** `assert_saved`, `db_session` and `browser_at` in `tests/e2e/conftest.py`;
`test_assert_saved.py` proving the helper fires on every toast the app can produce; the
post-BG flow rewritten to assert the row.

### What this story actually found
The browser suite already existed, already ran in CI, and already covered the broken form.
It did not fail because its assertion could not tell success from failure. **A UI test that
asserts on the existence of feedback is testing that the page has a `#toast` element.**

### Two things the strengthened suite then caught that review did not
1. **`corrections.js` rendered the server's message with no `✓`.** The drift guard on the
   success marker fired; without it the correction flow would have failed `assert_saved` and
   read, to whoever hit it, as *"the feature is broken"* when the feature was fine.
2. **★ The double-tap tests could not tell whether the idempotency key worked.** Found by an
   adversarial plant, not by reading: restoring per-submit minting left all four green.
   One test was satisfied by the disabled button; the other's second submit never fired at
   all, because a confirmed save clears the draft and the empty form was blocked by the
   timing check. It passed for the wrong reason. Both were rewritten around a **dropped
   response** — the server records the meal, the browser never learns — which no
   button-state change can satisfy.

  Chromium silently skips it (`scripts/verify.sh` says so out loud, CI installs Chromium).
