# S-1015 [SAFETY] — Serve a prediction when a meal is logged

**Epic:** 11 · **Safety story:** **Yes — INV-2 and INV-9** · **Status:** ✅ Done (2026-07-30) ·
**Requirements:** REQ-045, REQ-059, INV-2, INV-9 · **Records:** **DL-053** (+ its amendment), **DL-054** ·
**Unblocked by:** S-1014 · **Rollback baseline:** `6530075`

> `serve_meal_prediction` has existed since S-1008, is fully tested, and **no route calls
> it.** A grep across `api/` returns nothing. So logging a meal in the running app produces
> no prediction, `prediction_log` stays empty, shadow evidence never accrues, the 90-day
> clock never starts, and **Gate 1 can never open.**

## Story
Logging a meal produces a prediction that is **written to `prediction_log` and shown to
nobody**, so the evidence Gate 1 requires begins to accumulate.

---

## Written safety argument

This is the first time a model output exists in the running application. Two invariants
carry the weight, and they pull in **opposite directions** — which is exactly why this is a
`[SAFETY]` story rather than a wiring task.

### INV-2 — no patient-visible model output until Gate 1 passes

**The argument.** The prediction is written and never returned to any patient surface.
Specifically:

1. `POST /api/meals` returns `MealCreated` — `meal_id`, `test_at`, `message`. This story
   **adds no field to that response.** The schema is the boundary, and it is unchanged.
2. The patient readout (S-1002/S-804) is where display happens and where INV-2 is enforced;
   it is untouched here and still calls `build_patient_readout`, which refuses pre-Gate-1.
3. An **AST guard** asserts that `api/app.py`'s meal path does not put any prediction field
   into its response model.

**Why serving is nonetheless correct while the gate is shut.** Shadow mode *is* "the model
predicts, everything is logged, she sees nothing". That is the only mechanism by which the
evidence Gate 1 requires ever accumulates. Gating prediction here would stop the clock and
Gate 1 could never legitimately open — and **the deadlock would look like caution**, which
is the failure mode this project is least able to detect. S-1008 already records this;
`serve_meal_prediction` deliberately takes no gate argument and an existing AST guard
asserts it never calls `require_gate1`.

> **Prediction is not gated. Display is.** Getting that backwards fails in both directions.

### INV-9 — every prediction is written before it is returned

Already enforced inside `serve_prediction`: the row is flushed and its id confirmed before
any value is returned. This story's obligation is **not to catch what it raises.** A failed
write must propagate and fail the meal request, because the alternative is a prediction that
was served and not recorded — which is the exact thing INV-9 exists to prevent.

**★ And here is the tension this story must resolve explicitly.** Meal logging is her
primary capture surface. If a model error takes down `POST /api/meals`, she cannot log —
which is worse for her than having no prediction. But swallowing model errors would make
INV-9 unenforceable.

**Resolution (DL-053):** the meal is committed **first**, in its own transaction. The
prediction is then attempted in a **second** transaction, and:
- a `SafetyViolation` propagates — it means an invariant was breached and must be loud;
- **any other exception is caught, and the meal request still succeeds** — the meal is
  already durably recorded, and no prediction was served to anyone, so INV-9 is not at risk;
  a prediction that never happened cannot escape unlogged.

The asymmetry is deliberate and is the whole decision: **her data capture never depends on
the model working. Her safety invariants never depend on the model failing quietly.**

## Design

### `prescribe/live.py::predict_for_meal(session, meal, *, now)`
The composition root: profile → features → baseline → promoted model → guardrails → persist.
It reuses `data.training`'s derivation helpers so **the features served are assembled the
same way the features trained are** — a second, parallel feature path would drift, and the
drift would show up as a model that scores well and predicts badly.

- **Fails closed at every step.** No profile, no ICR, no promoted model, no stored model, or
  a feature the model was not fitted on ⇒ **no prediction**, no row, no error. The baseline
  is always computed and always available.
- Features are passed to `LoadedModel.predict_proba_for(..., feature_names=...)` so a
  mismatch is a refusal rather than a silently mis-indexed prediction (S-1014).
- `gate_state` records the live gate at the moment of prediction, so the log says what the
  world looked like when the row was written.

### `POST /api/meals` — one call, after the commit
The response model is unchanged.

## TDD strategy (SDET first — written and seen to fail)

`tests/safety/test_live_prediction.py`:
- **★ INV-2: the meal response contains no prediction.** Assert on the response **body**,
  and separately assert via AST that no prediction field was added to `MealCreated`. A body
  check alone passes if the field is present but null.
- **★ INV-2: the patient readout is still refused pre-Gate-1** after a prediction exists —
  the state this story creates for the first time.
- **★ INV-9: a prediction row exists after logging a meal**, with `meal_id` set, and
  `created_at` populated so the shadow clock can start.
- **★ A failing model does not stop her logging a meal.** Patch the model path to raise; the
  meal must still be recorded and `POST /api/meals` must still return 200.
- **★ …but a `SafetyViolation` still propagates.** The two must not be conflated: the test
  asserts a plain exception is swallowed *and* a `SafetyViolation` is not.
- **★ No promoted model ⇒ no prediction row and no error.** Today's real state.
- **★ The served features match the trained features** — the same assembly, asserted by
  comparing the served vector for a meal against `assemble_training_data`'s row for it.
- The shadow clock starts: `shadow_days` moves from 0 once predictions exist.

**RED evidence:** `prescribe.live` does not exist; `POST /api/meals` writes no
`prediction_log` row.

**Adversarial angle.** Four. (a) **Returning the prediction in the meal response** — the
single most natural thing to write, and a direct INV-2 breach. (b) **Wrapping the whole meal
handler in `try/except`**, which protects capture and silently disarms INV-9 and INV-6
together. (c) **Assembling features separately from `data.training`**, which drifts. (d)
**Serving before committing the meal**, so a model failure loses her meal.

## Outcome (BA, 2026-07-30)

**Done.** `prescribe/live.py`, one call from `POST /api/meals`,
`data.training.derive_meal_features` as the single feature derivation, and
`data.repositories.iob_from_prior_boluses`.

**`prediction_log` fills for the first time. The 90-day shadow clock starts.** The last link
in the DL-046 → DL-049 → S-1014 chain is connected: a promoted model predicts, every
prediction is recorded, and she sees none of it.

| Plant | Caught by |

### ★ Three defects found by running it, not by testing it
1. **The baseline double-counted her own pre-bolus** (DL-054). `07 §4` subtracts
   `meal_bolus_units` and `iob_at_meal` as separate terms, but a pre-bolus is timestamped
   *before* the meal, so the strictly-before rule counted the meal's own injection twice.
   **In the dangerous direction:** 5 U at ISF 30 pulls the baseline down 150 mg/dL, reading a
   hypo the physiology does not predict. INV-6 fired at a predicted BG of **7.6 mg/dL**.
2. **INV-6 then took down her meal logging.** Escalated, not decided — **the operator
   reversed part of DL-053**. An out-of-range baseline is now caught, the meal kept, the
   refusal recorded.
3. **Refusals were being scored as predictions**, reading as *"the model predicted no low"*.

### ★ An existing guard fired on the first attempt, and it was right
The DL-053 policy was first written as a `try/except` in the route, and the **S-1002 AST
guard** flagged it. The guard stayed untouched; the policy moved into **one named place**,
`predict_for_meal_safely`.

### ★ A process failure worth recording
The amendment and this close were **written, tested green, reported as committed and pushed —
and never landed.** The tool calls were interrupted; the reflog showed the commits did not
exist. It was caught only because a later story's test failed on behaviour that should have
been fixed. **The lesson: `git log` after a push is not ceremony. A reported commit is not a
commit.** Everything here was redone and verified present in the file before committing.

### Deviations from the design
- The live path could not reuse `assemble_training_data` — it filters to meals that already
  have an outcome, and the meal being predicted has none. `derive_meal_features` was
  extracted so both paths share one derivation without the training-set filter.
- `_ProbabilityModel.states` became a read-only property so a **frozen** wrapper satisfies it.

### Still open
- **No operator surface for refusals** (DL-053, unchanged). They leave a durable trace now,
  which is a precondition for a surface, but none has been invented.
- **`iob_at_meal` as a model *feature*** still includes the meal's own pre-bolus. Consistent
  between training and serving, so not a correctness bug — but collinear with
  `meal_bolus_units` for pre-bolused meals. Raised, not changed: altering a feature's
  definition changes the model.
